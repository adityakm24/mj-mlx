# Apple silicon hardware as a local-LLM target, and the competing Mac inference engines (state as of 21 November 2026)

Research method: web search and page reads only (no local measurement). Every number below is from the linked source; anything computed by me is under "Inferences". "Vendor" = self-reported by the engine/chip maker. Where a page could only be seen through a search snippet (fetch blocked), it is marked "(snippet only)".

## 1. Per-generation hardware facts (M1 to M6 / M5 Ultra): bandwidth, GPU, CPU matrix units, Neural Engine, memory, SSD, new accelerators

### Takeaway
Unified-memory bandwidth spans 68 GB/s (M1) to 1.2 TB/s (M5 Ultra, Aug 2026); the base chip has stayed on a 128-bit LPDDR bus since M1 (M6: only 170 GB/s). The big compute change is the M5 family's per-GPU-core "Neural Accelerator" (a matrix-multiply unit reached only via Metal 4 tensor ops), which gives ~4x prefill but does nothing for bandwidth-bound decode; the M4 family added SME2 on the CPU (~2 TFLOPS FP32 from one P-cluster unit), and M6 added a second 16-core Neural Engine.

### Inferences
- Per GB of bandwidth, the base tier has barely moved in six years (68 -> 170 GB/s, 2.5x) while GPU matrix compute rose >8x (Apple's M6-vs-M1 claim): on base and Pro chips decode is increasingly starved relative to compute, so idle compute during decode is the growing "unused resource".
- On Max/Ultra chips the ANE is capped near 120-150 GB/s regardless of system bandwidth (13-24% of it), so it cannot be a decode device there, but that bandwidth is additive to what the GPU pulls only if the DRAM is not already saturated.
- M6's two Neural Engines and Core AI's "use both simultaneously" claim suggest Apple is steering ANE toward concurrent side work (drafts, prefill of the next turn) rather than main decode.

## 2. What bounds decode vs prefill, published measurements, and distance from the bandwidth roofline

### Takeaway
Apple itself states the rule: time to first token is compute-bound, generation is memory-bandwidth-bound; M4->M5 gave ~3.3-4.1x TTFT but only 1.19-1.27x generation, tracking the 28% bandwidth increase. Direct measurements put the Apple GPU at roughly 76-80% of nominal DRAM bandwidth on base chips, and no engine's plain (non-speculative) decode exceeds the others by more than ~1.3x, so the remaining single-stream headroom is small except through speculative decoding, batching, or reading fewer bytes per token.

### Cited Findings
- "TTFT is compute-bound, while generation is memory-bandwidth-bound." M5 vs M4 MacBook Pro 24 GB, mlx_lm.generate, 4096-token prompt, 128 generated tokens: TTFT speed-up / generation speed-up: Qwen3-1.7B bf16 3.57x / 1.27x; Qwen3-8B bf16 3.62x / 1.24x; Qwen3-8B 4-bit 3.97x / 1.24x; Qwen3-14B 4-bit 4.06x / 1.19x; gpt-oss-20b MXFP4-Q4 3.33x / 1.24x; Qwen3-30B-A3B 4-bit 3.52x / 1.25x (memory 17.31 GB). — [Apple ML Research, 19 Nov 2025](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)
- llama.cpp table (Llama 2 7B, PP = 512-token prompt, TG = 128 tokens; old rows at Nov 2023 commit, M5-family and M6 rows at commit c1d0e7a), F16 PP / F16 TG / Q4_0 PP / Q4_0 TG in tok/s: M1 Max-32 600 / 23.0 / 530 / 61.2; M2 Ultra-76 1402 / 41.0 / 1238 / 94.3; M3 Ultra-80 1538 / 39.8 / 1471 / 92.1; M4 230 / 7.4 / 221 / 24.1; M4 Pro-20 464 / 17.2 / 440 / 50.7; M4 Max-40 923 / 31.6 / 886 / 83.1; M5 (Q8 PP 715, Q4_0) 723 / 31.9; M5 Pro-20 1589 / 21.6 / 1621 / 66.3; M5 Max-40 3158 / 37.1 / 3220 / 119.9; M5 Ultra-80 5207 / 73.6 / 4945 / 179.1; M6 953 / 11.6 / 989 / 35.7. ### Inferences
- Roofline check on the llama.cpp table (my arithmetic; assumes Llama-2-7B F16 = ~13.5 GB and Q4_0 = ~3.8 GB read per token, and nominal bandwidth): F16 decode reaches ~78-94% of bandwidth/bytes on single-die chips (M4 83%, M4 Pro 85%, M4 Max 78%, M5 Pro 94%, M5 Max 81%, M6 92%) and 69-81% on Ultras. Q4_0 decode reaches only ~75% on M5 Max, ~56% on M5 Ultra and ~45-60% on M2 Ultra. So: large-footprint dense decode is already at the roofline; small / quantized / sparse (MoE) decode on high-bandwidth chips is not bandwidth-bound and leaves a large fraction of DRAM bandwidth unused — it is bound by per-step overhead, dequantization compute and kernel dispatch.
- The MoE-on-Ultra results (M4 Pro >= M3 Ultra) point the same way: a 3B-active MoE at 4-bit reads only ~2 GB per token, so a 273 GB/s chip already has a ~130+ tok/s roofline and the Ultra's extra bandwidth is unused; MoE decode speed on big Macs is a latency/overhead problem, not a bandwidth one.
- Measured GPU streaming of ~80% of nominal on M4 means engines at ~85-94% of the nominal roofline for F16 are effectively at the hardware limit; the remaining levers are fewer bytes per token (lower-bit weights, skipping experts), more tokens per pass (speculative / MTP / batching), and removing idle gaps.

### Gaps
- No source gives a direct "fraction of roofline" analysis; BaseRT explicitly has none. Bytes-per-token figures for MoE models are not published.
- Tom's Hardware numeric tables (M4 Max and M5 Ultra pieces) could not be read (truncated/paywalled).
- No measured GPU streaming bandwidth for Pro/Max/Ultra chips was found (only base M3 and M4).

## 3. CPU-side opportunities: SME2 / Accelerate, CPU + GPU co-execution, measured contention on shared DRAM

### Takeaway
Three 2026 papers agree: CPU + GPU co-execution helps compute-bound prefill by ~1.2-1.4x and does nothing for memory-bound decode, because the two units fight for the same DRAM (co-run total on M4 tops out at ~95 GB/s, no better than GPU alone on large matrices). The CPU's SME unit is a real ~2 TFLOPS resource that Apple's own BNNS under-uses by 3-4.5x, and it is best for small-batch work with zero dispatch cost.

### Cited Findings
- M4 co-run measurements (GB/s read, CPU / GPU / both): 4096x4096: 66.1 / 54.3 / 73.9 (1.36x over GPU); 4096x14336: 68.9 / 80.3 / 91.3 (1.14x); 4096x28672: 71.5 / 88.9 / 93.4 (1.05x); 4096x128256: 72.0 / 96.7 / 95.4 (0.99x, "destructive bus arbitration"). Conclusion: heterogeneous CPU-GPU tensor parallelism in decode "yields negligible end-to-end speedup". — [EdgeAgent](https://arxiv.org/html/2610.03394)
- Same paper, prefill: GPU alone 232 tok/s, CPU alone 132 tok/s, together 304.5 tok/s at a 1024-token prompt (1.31x); TTFT at 4096 tokens 21.0 s -> 16.2 s. CPU SME kernel is used for small batches (M <= 16); zero-copy merge of CPU and GPU results gives ~1.14x decode. End to end with 4 agents: 33.6 tok/s (DeepSeek-R1-8B), 1.29x over batched baseline. No energy numbers. — [EdgeAgent](https://arxiv.org/html/2610.03394)
- FusionML (M1, M2, M3 Pro, M4, M4 Pro; mains power): per-layer CPU+GPU row split (CPU share 0.25-0.40) gives 1.15-1.38x on Llama-3-8B-shaped block prefill; through stock MLX-LM on Qwen2.5-7B bf16, TTFT improves 1.18-1.25x at 2k/4k/8k prompts; decode neutral (7.1 -> 7.1 tok/s M4; 13.4 -> 13.5 M4 Pro). — [FusionML, arXiv 2607.22785, 24 Jul 2026](https://arxiv.org/html/2607.22785)
- MLX-specific mechanism: MLX's lazy graph serializes CPU-stream and GPU-stream work when a CPU op consumes an unmaterialized GPU result: 0.66x (slower) with the lazy graph vs 1.34-1.38x with an eager materialization boundary. — [FusionML](https://arxiv.org/html/2607.22785)
- Contention: on M1 the GPU slows from 13.2 to 15.5 us/row when the CPU runs concurrently, so solo-unit rates overstate the best CPU share. Precision-matched training loses on all five chips (0.86-0.97x). — [FusionML](https://arxiv.org/html/2607.22785)
- Background bandwidth load: a saturating memory-stream workload slows batch-1 8B decode by 72% on a base M4; degradation vs memory pressure is convex. Lowering a background job's QoS (pushing it to E-cores) hurts decode more: +13.9 percentage points vs the same job on P-cores, because E-cores hold the memory fabric longer. — [The Gap Is the Loop, NeurIPS 2026](https://neurips.cc/virtual/2026/170048)
- PhaseGate: CPU pointer-chasing retrieval and GPU weight streaming "compete for memory service"; proposes admitting CPU retrieval only in LLM phases that tolerate it. — [PhaseGate, arXiv 2610.04537](https://arxiv.org/pdf/2610.04537) (snippet only)
- SME unit facts: one unit per cluster, a single core saturates it, peak chip throughput needs both P and E clusters; ~2 TFLOPS FP32 on the M4 P-cluster. — [tzakharko](https://github.com/tzakharko/m4-sme-exploration)
- Apple's BNNS reaches 19.0 GFLOPS at batch 1 vs 85.0 for a custom SME kernel, and 639 GFLOPS vs 2,070 at M=4096. Accelerate is 1.23x slower than a tuned SME GEMM on M4 Pro. — [EdgeAgent](https://arxiv.org/html/2610.03394); [MpGEMM](https://arxiv.org/html/2512.21473v1)
- Suggestion (untested) from the ANE reverse-engineering author: prefill on the ANE, decode on SME, because SME has zero dispatch overhead for single tokens. — [maderix](https://maderix.substack.com/p/inside-the-m4-apple-neural-engine-615)
- llama.cpp next-token agreement between its own CPU and GPU paths is only 96.5-97.8% (Splash's reference measurements), i.e. CPU/GPU splits change outputs at near-ties. FusionML reports token-identical output in 5 of 6 configs. — [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md); [FusionML](https://arxiv.org/html/2607.22785)

### Inferences
- For MoE decode on a high-bandwidth chip where the GPU is not saturating DRAM (section 2), the "decode is bandwidth-bound, so co-execution is useless" conclusion does not automatically hold: all three papers tested dense models on base / Pro chips (68-273 GB/s). Nobody has published CPU-side expert execution or CPU-side sampling for MoE on a Max/Ultra, where DRAM headroom exists. This is an untested gap, not a demonstrated win.
- Any CPU + GPU scheme inside MLX must insert explicit evaluation boundaries or it will run slower than GPU-only.
- Background work should be kept on P-cores or stopped during benchmarks; QoS demotion is counter-productive for decode.

### Gaps
- No measurement of combined CPU + GPU bandwidth on Pro/Max/Ultra chips, where the CPU cluster count and memory channels differ.
- No published energy comparison for CPU-assisted prefill (FusionML and EdgeAgent report none).
- No published work found that runs MoE experts or sampling on the CPU while the GPU runs attention on Apple silicon (the closest is NPUMoE, which uses the NPU, and llama.cpp's CPU-expert offload, which is aimed at >RAM cases).

## 4. Neural Engine: Core ML / Core AI support for LLMs, ANE-based projects, speeds, energy, limits

### Takeaway
Core AI (WWDC, June 2026) replaced Core ML for neural networks and adds in-place state (KV cache), dynamic shapes, ahead-of-time compile and custom Metal 4 kernels, but publishes no LLM performance or ANE placement controls. Every measurement agrees the ANE is a tokens-per-joule device, not a tokens-per-second one: 2-5x slower than the GPU for decode, ~5-10x lower power, capped at roughly 55-150 GB/s and 512-4096 tokens of context, with heavy fixed-shape, compile-time and dispatch constraints; the wins published so far are prefill offload (NPUMoE: 1.8-7.4x energy; Splash 1.3: 1.14x TTFT on M5 Max).

### Cited Findings

Core AI / Core ML
- Core AI announced at WWDC26 as the on-device inference framework behind Apple Intelligence, running on CPU, GPU and Neural Engine through one API; Apple engineers say neural networks should move to Core AI while Core ML remains for classic ML (trees, pipelines). Apple cites models from 3B vision models to reasoning LLMs "up to 70B parameters". — [InfoQ, 20 Jun 2026](https://infoq.com/news/2026/06/apple-core-ai-wwdc); [Apple developer forum "Core ML RIP?"](https://developer.apple.com/forums/thread/831715)
- Session 324 details: KV cache implemented as Core AI "states" (inputs read and updated in place; fixed-size, sized for a maximum context); dynamic sequence dimension via `torch.export.Dim` (example min 1, max 256); models are device-agnostic and "specialized" on first load (can take long for large models; artifacts tied to device and OS version); `AIModelCache`, explicit `AIModel.specialize`, AOT compilation on the dev machine; custom GPU kernels via Metal 4; a Core AI Language model API plugs into Foundation Models. No API to choose compute units, no quantization formats and no performance numbers are given. — [WWDC26 session 324](https://developer.apple.com/videos/play/wwdc2026/324/)
- Quantization and palettization are applied during conversion with `coreai-torch`; composite ops include attention, RoPE, RMSNorm, gather-matmul. — [InfoQ](https://infoq.com/news/2026/06/apple-core-ai-wwdc)
- Apple's own Core ML LLM result targeted the GPU, not the ANE ("because the model is memory-bandwidth bound"): Llama-3.1-8B on M1 Max, macOS 15.2 beta: 0.19 tok/s baseline -> 16.26 tok/s with KV cache as state -> 33.67 tok/s with block-wise Int4 (block 32), 4.2 GB. — [Apple ML Research, 1 Nov 2024](https://machinelearning.apple.com/research/core-ml-on-device-llama)
- On macOS 26.3, Core ML `compute_units=ALL` routed a Qwen3.5 prefill model to the GPU, not the ANE (ANE power ~0 W). — [AtomGradient hybrid bench](https://atomgradient.github.io/hybrid-ane-mlx-bench/)
- Core ML is the only documented route to the ANE; a direct route below Core ML from a user process exists but is undocumented and breaks across OS updates. — [Bryngelson, arXiv 2606.22283 (303 pages; v2 15 Oct 2026)](https://arxiv.org/abs/2606.22283)

Per-call overhead and limits
- Direct private-API dispatch ~0.095 ms per call (XPC + IOKit); Core ML adds 2-4x for small ops; ops under ~1 ms are dispatch-dominated; a 119-compile limit exists. — [maderix](https://maderix.substack.com/p/inside-the-m4-apple-neural-engine-615)
- Core ML dispatch measured at ~20-24 ms fixed + ~7 us/row, "which excludes layer-granularity use"; batch-scale FFN matmuls on ANE: 1.61-1.79x burst, 1.16-1.29x sustained. — [FusionML](https://arxiv.org/html/2607.22785)
- NPU constraints (M2 Max / M2 Ultra): static shape-specific graphs compiled ahead of time; dynamic shapes fall back to CPU; many small graphs serialize on one device queue; graphs above ~1.2 GB on M2 Ultra fall back to CPU; Core ML fixes placement at compile time; CPU-NPU synchronization can exceed 60% of run time. — [NPUMoE, arXiv 2604.18788, 20 Apr 2026](https://arxiv.org/html/2604.18788)
- ANEForge reports a ~2 GB single-program ceiling (auto-segments larger models). — [runaihome](https://runaihome.com/blog/apple-neural-engine-llm-inference-2026/)
- Core ML compile for fixed-length prefill models: ~103 s (seq 64), 50 min (seq 256), 97 min (seq 512), cached afterwards; prompts over 512 tokens need bigger variants; hybrid storage +128%. — [AtomGradient hybrid bench](https://atomgradient.github.io/hybrid-ane-mlx-bench/)
- ANEMLL 0.3.5 beta: Core ML pipeline, chunked models, LUT4 (FFN) / LUT6 (LM head) palettization, in-model argmax; context 512-4096 (512-1024 recommended; M1 limited to 512); FP16 range overflow on Gemma 3; "LUT4 quality is fairly low because the ANE lacks block quantization"; supports up to 8B models. No Core AI support or hybrid GPU work mentioned. — [ANEMLL](https://github.com/anemll/anemll)
- An M3 ANE erratum: weight transfers that are exact multiples of 1 MiB per core fall to 17-19 GB/s from 45-60; splitting into 512 KiB chunks restores it; 7 of 15 ANEMLL models hit it; after the fix Llama 3.2 1B went 10.0 -> 24.3 tok/s and Qwen3-8B 1.36 -> 2.97 tok/s on a base M3. — [runaihome / Yoon, Aug-Sep 2026](https://runaihome.com/blog/apple-neural-engine-llm-inference-2026/)

Speeds and energy
- ANE decode: 1B models 47-62 tok/s on newer chips, 8B ~9 tok/s, vs >93 tok/s for 8B on the same machine's GPU (2-5x GPU advantage); ANEForge Qwen3-0.6B ~75 tok/s with resident KV cache, speculative decoding adds 2.28x. — [runaihome](https://runaihome.com/blog/apple-neural-engine-llm-inference-2026/)
- M2 Ultra, Qwen3.5-0.8B: ANE private-API decode 22.8 tok/s vs MLX GPU 69.0; ANE batch prefill (32 tokens/call) 268 tok/s vs sequential 23.7 (11.3x) but MLX GPU prefill is 736 tok/s at 74 tokens. Power: GPU prefill 62.05 W GPU + 2.34 W CPU; GPU decode 14.17 W + 2.98 W; ANE prefill 1.58 W ANE + 3.77 W CPU (5.57 W total); ANE decode 7.05 W total. ANE->MLX state hand-off costs ~27 ms. ANE can prefill the next turn while the GPU decodes: TTFT 27 ms on later turns vs 101 ms pure MLX, but hybrid decode is slower and total time is not better. — [AtomGradient batch prefill](https://atomgradient.github.io/hybird-batch-prefill-on-ane); [AtomGradient hybrid bench](https://atomgradient.github.io/hybrid-ane-mlx-bench/)
- NPUMoE (prefill of MoE models on the ANE; attention and expert FFNs on NPU; routing, top-k, scatter/gather, LayerNorm on CPU; GPU unused): 1.32-5.55x lower latency, 1.81-7.37x better energy, 1.78-5.54x fewer CPU cycles than Core ML baselines (Core ML CPU, Core ML default, ANEMLL) on Phi-3.5-MoE 42B, Phi-tiny-MoE and Qwen3-30B-A3B. Qwen3-MoE on M2 Ultra: 0.572 s vs 1.139 s; 3.80 J vs 12.67 J. Versus the GPU on an attention + MoE block: GPU 0.99 s, 54.72 J, 54.29 W; NPUMoE 1.26 s, 12.21 J, 9.61 W. Uses static expert-capacity tiers (10-20% token dropping costs ~1% accuracy; 31.7-37.5% of tokens are padding). Decode is not optimized ("memory-bound and doesn't amortize CPU-NPU coordination"). No MLX or llama.cpp baseline. — [NPUMoE](https://arxiv.org/html/2604.18788)
- Splash 1.3.0 runs Qwen3.8-27B prefill feed-forward layers across GPU and Neural Engine, calibrating the split per Mac and model; cold-prompt TTFT on M5 Max 14.09 s -> 12.36 s (1.14x) on MLX 4-bit weights; headline "1.49x". ANE prefill is on by default for the 27B (`--disable-ane` to turn off). Access path not documented. — [AlphaSignal on Splash 1.3.0](https://alphasignal.ai/news/inco-ai-s-splash-1-3-0-cuts-mac-prefill-wait-by-1-49x-for-coding-agents) (snippet only); [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md)
- uzu's prefill lead over BaseRT on M4 Pro is attributed by the BaseRT authors to MPSGraph, "which can dispatch to the Apple Neural Engine". — [BaseRT](https://arxiv.org/html/2607.00501)
- M4 Max power: Core ML / ANE 12.7 W vs MLX / GPU 24.7 W. — [insiderllm guide](https://insiderllm.com/guides/apple-neural-engine-llm-inference/) (snippet only)

### Inferences
- The ANE's realistic roles are (a) low-power prefill or draft work running concurrently with GPU decode, and (b) FFN-heavy prefill split with the GPU (Splash's choice). Its bandwidth cap (section 1) and 32 MB SRAM rule it out for main decode of multi-GB models.
- Gains are small where the GPU has Neural Accelerators (1.14x on M5 Max); the ANE split is most valuable on pre-M5 chips, where GPU prefill is 4x slower.
- No project has published ANE use during MoE decode; NPUMoE shows expert FFNs can live on the NPU for prefill but needs capacity tiers and token dropping, i.e. it is not exact.

### Gaps
- "Anemll-Forge" as an ANEMLL project: not found. The Forge-named work found is ANEForge (Bryngelson, arXiv 2606.17090), a separate direct-ANE Python project; no ANEMLL hybrid GPU + ANE results were found.
- SIP: no source read says the ANE private API needs SIP disabled (maderix and Bryngelson run from a normal user process). SIP came up only for persisting sysctl / boot-args.
- Apple's own on-device foundation-model speeds and energy: not sourced this session.
- Core AI: no published LLM tok/s, no documented compute-unit control, no stated context or model-size limits; whether Core AI states run on the ANE is not stated.
- ANEMLL-bench per-model tok/s tables (Results.MD) were not read.

## 5. Storage as memory: SSD throughput and latency, file-system / page-cache behaviour, published >RAM work on Macs

### Takeaway
Internal SSDs read 2-3 GB/s (M1-M4 base) to ~6.5 GB/s (M5), i.e. 25-200x below DRAM bandwidth, so SSD-streamed dense models run at 0.2-0.3 tok/s while MoE expert streaming with caching reaches 12-30 tok/s for a 30-35B-A3B model on 16-36 GB Macs and 12-19 tok/s for 145-178 GiB models on a 128 GB M5 Max. Published implementations converge on `pread` into a fixed pool of Metal buffers (not mmap paging), prediction/prefetch of experts, and keeping non-expert weights resident.

### Cited Findings
- SSD numbers: see section 1 (M5 MBP ~6.3-6.6 GB/s read vs M4 ~2.0 GB/s; M1 Max ~5.1 GB/s; M1 mini 2.9 GB/s median and ~0.5 GB/s on small files).
- macOS serves just-written or recently read files from memory, inflating read benchmarks (10.8 GB/s "reads" on an M1); "particularly when dealing with files smaller than 2 MB, macOS and storage devices go out of their way to improve their performance using fast memory". — [Eclectic Light 2020](https://eclecticlight.co/2020/12/28/internal-ssds-can-read-files-at-extreme-speed/); [Eclectic Light 2022](https://eclecticlight.co/2022/05/06/interpreting-and-using-disk-performance-data/)
- A 2026 benchmark tool author argues Blackmagic and AmorphousDiskMark do not set F_NOCACHE and can measure RAM on large-memory Macs; challenged in-thread; no numbers published. — [MacRumors forum, Apr 2026](https://forums.macrumors.com/threads/beta-disktruth-f_nocache-mac-disk-benchmark-slc-cliff-detection-negotiated-interface-speed-testflight-now-open.2481094/)
- llama.cpp RFC + PoC (19 May 2026): fixed pool of N expert slots per MoE layer in Metal shared memory; a Metal kernel publishes routed expert IDs; a CPU sidecar thread maps experts to slots (LRU; SLRU no better) and loads misses with `pread`; an `MTLSharedEvent` signals the GPU; needs `--no-mmap` and `--no-warmup`; exact (no dropped experts). Qwen3-30B-A3B Q6_K on M3 Pro 36 GB: vanilla 38.1 tok/s at ~27.2 GiB wired; 128 slots 30 tok/s; 80 slots 29.1 tok/s at 18.9 GiB; 32 slots 22.1 tok/s at 10.6 GiB; 8 slots 12 tok/s at 6.3 GiB; ~13 tok/s on M1 Pro 16 GB. Author: wired memory "can't be compressed or swapped" and Metal must wire buffers before execution, so OS paging "does not work as good here". No maintainer response. — [llama.cpp discussion #23324](https://github.com/ggml-org/llama.cpp/discussions/23324)
- Same thread, a non-Mac data point: 16 MiB overlapped reads sustained 2.80 GB/s vs 377 MB/s through mmap paging (PCIe 3.0 NVMe, Windows); pinning 24 GiB on a 32 GB machine collapsed throughput to 0.12 tok/s. — [llama.cpp discussion #23324](https://github.com/ggml-org/llama.cpp/discussions/23324)
- AiiStream Q3.6 (1 Oct 2026, Apache-2.0): Qwen3.6-35B-A3B 4-bit on a 16 GB M5 MacBook Air at 15.0 tok/s (11.8 with other apps open), ~2.3 s to first token, ~1.7 GB of MLX memory; experts stay on SSD, next-layer experts are predicted and loaded early; "72.6% faster than direct SSD streaming"; byte-identical to stock mlx_lm at fixed seed. 8 GB figures are estimates. — [Hugging Face forum](https://discuss.huggingface.co/t/running-qwen3-6-35b-a3b-on-a-8-16-gb-mac-at-15-token-s/182775)
- Hypura (GGUF, Rust): tiers = GPU working set / RAM via mmap / NVMe via `F_NOCACHE` + `pread` with prefetch. M1 Max 32 GB: Mixtral 8x7B Q5_K_M (30.9 GB) 2.2 tok/s where llama.cpp OOMs; Llama 3.3 70B Q4_K_M (39.6 GB) 0.3 tok/s (dense FFN streaming); claims 99.5% neuron-cache hit rate and 75% I/O reduction from router interception. — [Hypura](https://github.com/t8/hypura)
- ds4 / DwarfStar (antirez), 6 Sep 2026, 128 GB M5 Max, automatic expert cache, no speculative decoding: GLM 5.3 Flash Q4_K (177.77 GiB): prefill 121 tok/s, generation 11.9-14.9 tok/s; DeepSeek Flash Vision MXFP4 (145.26 GiB): prefill 300 tok/s, generation 11.9-19.3 tok/s with an 86.2 GiB expert cache. Notes: generation is more sensitive to cache misses than prefill; on Metal, non-routed weights must stay resident and an oversized expert cache evicts them and slows decode; expert preloading should stay on. I/O calls not documented. — [ds4 SSD_STREAMING.md](https://raw.githubusercontent.com/antirez/ds4/master/docs/SSD_STREAMING.md)
- MLX-Flash (MIT; docs dated Oct 2026): replaces MLX `QuantizedSwitchLinear` with a GPU lookup table over pre-stacked expert tensors; reads `vm_statistics64` each call and shrinks its cache under pressure; `madvise(MADV_FREE)` on evicted weights (~20% less pressure, vendor); Qwen3-30B-A3B 4-bit on M3 Max 36 GB with apps open: 82.6 tok/s vs ~3 tok/s for a swapping Ollama; 64 of 128 experts cached gives 85%+ hits and ~15 tok/s; a 209 GB model on a 64 GB Mac at 4.4 tok/s. Several headline figures are flagged by the project as estimates/roadmap. — [MLX-Flash](https://github.com/szibis/MLX-Flash)
- Apple DTS (Kevin Elliott, Dec 2025-Feb 2026): anonymous memory is compressed before it is swapped; total swap is capped by a kernel limit derived from RAM (16 GB Mac: ~40-45 GB of swap, then the process is killed even with 470 GB of disk free); page size is 16 KB; `mmap` with `MAP_SHARED` on a file "bypasses the swap cap" (file-backed, no compression); the `vm_compression_limit` boot-arg can raise the cap but "WILL create problems" (hangs, panics). — [Apple developer forum thread 809830](https://developer.apple.com/forums/thread/809830)
- oMLX and LM Studio use the SSD for KV cache rather than weights: oMLX offloads cold KV blocks to SSD as safetensors (TTFT 30-90 s -> 1-3 s, author's anecdote); LM Studio mlx-engine 1.8.5 writes KV at every 256-token boundary to an LRU scratch file. — [oMLX in MLX discussion #3203](https://github.com/ml-explore/mlx/discussions/3203); [LM Studio blog, 5 Jun 2026](https://lmstudio.ai/blog/mlx-engine-agentic-workloads)
- Background: Simon Willison covered "streaming experts" on 24 Mar 2026; a "TurboFieldfare" project claims a 26B model in 2 GB of RAM (not independently verified). — [simonwillison.net](https://simonwillison.net/2026/mar/24/streaming-experts); [Better Stack guide](https://betterstack.com/community/guides/ai/turbo-fieldfare/) (snippet only)

### Inferences
- With ~150 MB-class expert blocks at 4-6 bits, one cold expert read costs ~25-70 ms at 2-6 GB/s; published designs therefore win by cache hit rate and prediction, not raw SSD speed. The M5's 3x faster SSD shifts the break-even slot count down markedly (the 15 tok/s on a 16 GB M5 Air vs 13 tok/s on a 16 GB M1 Pro are not comparable setups, but both sit in the same band).
- Everyone who measured avoids mmap page-fault paths for GPU-visible weights: Metal wires whole buffers, and wired pages are neither compressed nor swapped, so the OS cannot page experts behind the GPU's back.
- File-backed shared mappings are the only way around the swap cap for >RAM data, but they must stay off the GPU-wired path.

### Gaps
- No published 4 KB to 1 MB read-size latency curves for M-series internal SSDs; no Mac measurement of mmap-fault throughput vs `pread` (the only number is from a Windows machine). A "direct I/O 27% faster than mmap because of the unified buffer cache" claim surfaced in search but its source page was not identified.
- No documentation found on `F_RDADVISE`, `madvise(MADV_WILLNEED)` or `mlock` behaviour with Metal no-copy buffers in any engine's notes.
- No source measures SSD energy cost per token for streaming.

## 6. macOS memory management that affects inference: compression, swap, jetsam, GPU wired limit

### Takeaway
GPU-visible memory is wired, cannot be compressed or swapped, and is capped by an undocumented system limit (`iogpu.wired_limit_mb`; MLX documents how to raise it); when wired memory crowds out the rest, the failure is often a kernel panic in IOGPUMemory rather than a clean jetsam kill. Anonymous memory is compressed then swapped up to a RAM-derived cap, after which the kernel kills the process.

### Cited Findings
- MLX docs: `mx.set_wired_limit(limit)` sets "the total size in bytes of memory that will be kept resident"; default 0; setting it above the system wired limit is an error; raise the system limit with `sudo sysctl iogpu.wired_limit_mb=<MB>`; the limit "should remain strictly less than the total memory size"; only useful on macOS 15.0+; `device_info()` reports `max_recommended_working_set_size` and `memory_size`. — [MLX documentation](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html)
- Community notes on the sysctl: 0 means "system default" (roughly 75% of RAM on larger machines), not unlimited; older macOS used `debug.iogpu.wired_limit`; undocumented by Apple; resets at reboot unless persisted; advice is to leave 8-16 GB for macOS. — [devnote-override-macos-metal-vram-cap](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap) (snippet only)
- mlx-lm issue #883 (12 Feb 2026): `mlx_lm.server` with Qwen3-Coder-30B-A3B 8-bit and a ~58k-token KV cache on an M3 Ultra 96 GB, macOS 26.3: full kernel panic ("completeMemory() prepare count underflow", IOGPUMemory.cpp:550) at 80.14 GB wired (83.5%), 0.01 GB free; memory pressure was never flagged. Maintainer: "probably related to the wired limit being too high"; long-term fix is to expose/offload prompt caches to disk; `--max-kv-size` merged (PR #906). Further panics reported on macOS 26.4 (nine in six days, 122B MoE, default sysctl) and in Sep 2026 on a 24 GB Mac (27B 4-bit at 64k context, blamed on KV reallocation in 256-token steps). — [mlx-lm issue #883](https://github.com/ml-explore/mlx-lm/issues/883)
- XNU's memorystatus documentation lists jetsam kill reasons including high-water-mark, VM page shortage, compressor thrashing and compressor space shortage, with most kills proceeding in ascending jetsam priority. — [XNU doc/vm/memorystatus_kills.md](https://cs.iossec.tech/xnu/latest/source/doc/vm/memorystatus_kills.md) (snippet only; page blocked)
- Swap cap and compression behaviour: see Apple DTS thread in section 5. — [Apple developer forum thread 809830](https://developer.apple.com/forums/thread/809830)
- Engines that manage memory explicitly: oMLX enforces a process memory limit defaulting to RAM minus 8 GB; vllm-metal has `--gpu-memory-utilization` and queues requests when the KV pool is full; Splash has `--max-memory`, `--idle-release` (10 min); ds4 has a memory guard that refuses requests. — [oMLX](https://github.com/jundot/omlx); [vllm-metal blog](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0); [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md); [ds4](https://raw.githubusercontent.com/antirez/ds4/master/docs/SSD_STREAMING.md)
- SiliconBench memory audit (M5 Pro 64 GB): Ollama holds 94-97% of Metal's advisory working-set hint from concurrency 1; mlx_lm nearly triples its chat footprint for a 7% throughput gain; vllm-mlx climbs; mistral.rs reached 59.3 GB while completing 13/100 requests; padding in an mlx_lm batch wasted 61% of compute and KV I/O and on a 32 GB M1 Pro triggered page compression and a 2.5x slowdown. llama.cpp and vllm-metal stay flat. — [SiliconBench, arXiv 2609.19169](https://arxiv.org/html/2609.19169)
- On an 8 GB M1, probing an alternative execution mode evicts the active mode's working set: ~1.4x inflated readings and ~1.7x reload cost on the next call. — [FusionML](https://arxiv.org/html/2607.22785)

### Inferences
- "Leave headroom" is the only guidance that exists; neither Apple nor MLX publishes a safe wired fraction. The observed failure points (83.5% wired on 96 GB; default limit on macOS 26.4) suggest staying well below the default ~75% GPU limit when KV cache can grow.
- A process that holds most wired memory is not protected by ordinary memory-pressure signalling (pressure was "false" at panic), so engines must self-limit rather than rely on jetsam.

### Gaps
- The exact jetsam rule for a process holding a large share of wired memory was not found (XNU docs page was blocked; no Apple statement). The default formula for `iogpu.wired_limit_mb` by RAM size is not documented.
- Apple has published no guidance specific to LLM workloads beyond the MLX docstring.
- Whether macOS 26.4+/27 changed IOGPU wired-memory behaviour or fixed the panics: no source.

## 7. Thermal and power: sustained vs burst, power at full GPU load, power modes, battery vs AC

### Takeaway
Wall power at full load ranges from ~145 W (M4 Max Mac Studio) to 385 W (M5 Ultra); measured GPU package power is ~14 W for small-model decode and ~54-67 W for prefill on an M2 Ultra, and the ANE runs the same work at 1.5-10 W. Evidence on fanless throttling is thin and mostly low quality; the best controlled data point is a fanless M1 whose 1.79x burst gain decays to 1.16-1.29x sustained.

### Cited Findings
- Apple wall-power table (idle / max W): Mac Studio M5 Max 7 / 200; M5 Ultra (80-core GPU, 512 GB) 9 / 385; M4 Max 6 / 145; M3 Ultra 9 / 270; M2 Ultra 10 / 295; M1 Ultra 13 / 215; M1 Max 11 / 115. Measured at the wall at 20.2 C ambient. — [Apple support 102027, 22 Sep 2026](https://support.apple.com/en-gb/102027)
- Power modes: Low Power Mode reduces energy use (and fan noise on fanned models); High Power Mode lets fans run faster and "may allow higher performance during very intensive workloads" (Mac Studio 2026, Mac mini with Pro chip, MacBook Pro with Pro/Max 2024+ and Max 2021-2023); separate settings for battery and adapter; no quantified effects. — [Apple support 101613, 5 Nov 2026](https://support.apple.com/en-mt/101613)
- Component power on M2 Ultra (powermetrics-style): MLX GPU prefill 62.05 W GPU; GPU decode 14.17 W (0.8B model); full inference on a 9B model with long prompt 53.2 W total; 2B 8-bit 39.6 W. — [AtomGradient](https://atomgradient.github.io/hybrid-ane-mlx-bench/)
- GPU vs NPU on M2-class hardware: dense attention kernel GPU 66.80 W (7.09 ms, 516 mJ) vs NPU 7.10 W (38.27 ms, 276 mJ); attention + MoE block GPU 54.29 W vs 9.61 W. — [NPUMoE](https://arxiv.org/html/2604.18788)
- Thermal decay: on the passively cooled M1, sustained load lowers CPU+GPU co-execution gains and ANE batch matmul gains fall from 1.79x burst to 1.16-1.29x sustained; the M1 "fades" at 8192-token prefill. — [FusionML](https://arxiv.org/html/2607.22785)
- Actively cooled M2 Pro sustains higher clocks than the passive M2 Air at the same 102.4 GB/s bandwidth (qualitative); thermal effects were handled only by warm-up runs. M3 Ultra achieves "up to 23 times" the tokens per joule of an RTX 5090 (absolute values omitted). — [Silicon Showdown](https://arxiv.org/html/2605.00519v1)
- M4 Pro 48 GB with Ollama: total system power 8-12 W during sustained inference of 3-9B models; smaller models use up to 62% less energy per token; a "CPU+GPU package power about 0.47 W" figure also appears. — [GreenBench, arXiv 2608.28667, 24 Aug 2026](https://arxiv.org/abs/2608.28667)
- M5 Ultra Mac Studio vs DGX Spark on an agentic task (Qwen 3.8 27B with MTP, llama.cpp): Mac finished in just under half the time, used ~16% less task energy, energy-delay product under half. — [Tom's Hardware, 10 Nov 2026](https://www.tomshardware.com/tech-industry/artificial-intelligence/going-deep-on-local-ai-performance-with-apples-mac-studio-with-m5-ultra-inference-engine-recipes-mandatory-for-bigger-models-as-mlx-stack-matures)
- Four M3 Ultra Mac Studios under exo: "under 250 watts"; single unit idles under 10 W. — [Jeff Geerling](https://jeffgeerling.com/blog/2025/15-tb-vram-on-mac-studio-rdma-over-thunderbolt-5)
- Fanless Air claims (blogs / community logs, methods unclear, mutually inconsistent): M5 Air throttles within 8-15 min from ~35 to ~13 tok/s; M4 Air drops 15-20% after 10-12 min on 14B+ models; another test finds only ~6% drop over five all-core rounds. — [craftrigs M4 Air test](https://craftrigs.pages.dev/guides/macbook-air-m4-thermal-throttling-30min-test/); [solidaitech M5 Air](https://www.solidaitech.com/2026/04/m5-macbook-air-local-ai-thermal-throttle-problem.html) (both snippet only)
- A submitting CPU core that downclocks between tokens costs 9-12% decode speed; light background load can mask this by keeping cores awake. — [The Gap Is the Loop](https://neurips.cc/virtual/2026/170048)

### Inferences
- GreenBench's 0.47 W package figure is implausible next to its own 8-12 W system figure and the 14-62 W GPU figures elsewhere; treat it as a measurement artefact (likely averaged over idle time or the wrong powermetrics field).
- Because decode is bandwidth-bound and draws far less GPU power than prefill (14 W vs 62 W on M2 Ultra), throttling should hit prefill and long batched work first; published throttling anecdotes do not separate the two.

### Gaps
- No controlled measurement found of Low Power Mode, High Power Mode, or battery vs AC effect on LLM tokens/s or J/token.
- No published sustained-load GPU power for M5-family chips with Neural Accelerators active.
- No published benchmark states the power mode used; only FusionML states "mains power".

## 8. Competing Mac engines in 2026: architecture, accelerators, techniques, best published numbers

### Takeaway
The field split in 2026 into (a) general MLX-based servers (mlx-lm, LM Studio's mlx-engine, Ollama's MLX runner, vllm-mlx, vllm-metal, oMLX, exo), (b) llama.cpp Metal, and (c) new native-Metal, per-model engines (Splash, uzu, BaseRT, Magnitude, Locals, ds4) whose headline wins come from trained draft models / MTP speculative decoding, M5 tensor-op prefill kernels, INT8 KV, and SSD-backed prefix caches. Plain decode differs by at most ~1.3x between engines; the 2-5x claims all involve speculative decoding or caching. Almost no engine publishes energy.

### Cited Findings

llama.cpp (Metal)
- GGUF, hand-written Metal kernels, KleidiAI SME2 on CPU. Community table in section 2. Slowest of the three on M5 Pro decode for Qwen3.6-35B-A3B Q4 (63.1 vs MLX 101.9, BaseRT 110.7) and far behind on M5 prefill for small models (Gemma-4-E2B pp2048 2,656 vs MLX 13,187). — [BaseRT M5](https://arxiv.org/html/2607.19438); [Arm](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/performance_llama_cpp_sme2/introduction/)
- MTP speculative decoding (`--spec-type draft-mtp`) on Metal: an M1 Max bug report finds it slower than baseline at every setting (11% slower even at 100% acceptance; up to 28% slower at n_max=6 with 43% acceptance); a later vendor post claims merged Metal kernels reach 110 vs 32.1 tok/s on M3 Ultra (unverified). Splash's own comparison: 27B on M5 Pro 16 tok/s plain, 27 with MTP. An M1 Max test in Oct 2026 shows MTP helping: Qwen3.5-9B 36.6 -> 48.5 tok/s (short), 37.1 -> 60.2 (code), 31.4 -> 32.5 (27K context). — [llama.cpp issue #23752](https://github.com/ggml-org/llama.cpp/issues/23752) (snippet only); [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md); [lilting.ch, 28 Oct 2026](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)
- Stable memory under load and one of three engines passing all SiliconBench gates; throughput plateaus with concurrency. — [SiliconBench](https://arxiv.org/html/2609.19169)

mlx-lm (Apple)
- Reference MLX implementation; uses M5 Neural Accelerators on macOS 26.2+; pipelined async decode loop. M4 Max 128 GB 4-bit: Qwen3-30B-A3B 107.4 tok/s, Qwen3-8B 79.9, Qwen3-0.6B 356.2. M5 Pro: Qwen3.6-35B-A3B Q4 101.9 tok/s decode, 596 tok/s pp128. Weak batching: padding wastes 61% of compute in uneven batches; at concurrency 4 on Qwen3.6-35B-A3B it completed only a minority of requests; memory grows unbounded. — [vllm-mlx paper](https://arxiv.org/html/2601.19139); [BaseRT M5](https://arxiv.org/html/2607.19438); [vllm-metal blog](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0); [SiliconBench](https://arxiv.org/html/2609.19169)

LM Studio
- Two general engines (llama.cpp, mlx-engine) plus the Splash engine since Sep 2026. mlx-engine 1.8.5 (5 Jun 2026): KV checkpoints every 256 tokens streamed to a disk LRU, longest-prefix restore, continuous batching; on M3 Max 36 GB with Qwen3.6-27B 4-bit, four parallel chats 15.24 -> 33.97 output tok/s; 82% less extra RAM on four 32,876-token prompts. Apple quotes LM Studio prompt processing on M5 Max as 3.9x M4 Max and M5 Ultra as 4x M3 Ultra. — [LM Studio blog](https://lmstudio.ai/blog/mlx-engine-agentic-workloads); [Apple newsroom Mac Studio](https://www.apple.com/my/newsroom/2026/08/apple-introduces-mac-studio-with-m5-max-and-m5-ultra/)
- Independent M4 Mac mini 24 GB test (Nov 2026): LM Studio MLX engine 1.13.1 20.1 tok/s vs mlx-lm 21.3 on the same 4-bit file; its MTP flag made no noticeable difference. — [computingforgeeks](https://computingforgeeks.com/?p=181447) (snippet only)

Ollama (MLX runner)
- 0.19 preview 30 Mar 2026; MLX default on Apple silicon from 0.30 (13 May 2026). Vendor numbers for Qwen3.5-35B-A3B (chip not named, >32 GB required): prefill 1,154 -> 1,810 tok/s and decode 58 -> 112 tok/s, but comparing Q4_K_M on the old engine with NVFP4 on MLX; int4 projected 134 tok/s. 11 Jun 2026 update: kernel fusion via MLX JIT, GPU sampling, state snapshots at branch points, NVFP4 ~20% faster output than Q4_K_M on Gemma 4 12B / M5 Max. Uses M5 Neural Accelerators. Speculative draft heads auto-enable and cannot be turned off. — [Ollama blog 30 Mar 2026](https://ollama.com/blog/mlx); [Ollama blog 11 Jun 2026](https://ollama.com/blog/mlx-performance); [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)
- Independent: M4 24 GB, qwen3.5:9b: MLX runner 16.1 tok/s, 27.3 with MTP drafting, vs 17.1 for the llama.cpp GGUF build. M1 Max: 47-53 tok/s decode, no scaling with concurrency (53-55 tok/s at 2-8 streams). SiliconBench: fidelity failure in 5-shot (0.4462 vs 0.7364 reference) and 94-97% of the Metal memory hint held. — [computingforgeeks](https://computingforgeeks.com/?p=181447) (snippet only); [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark); [SiliconBench](https://arxiv.org/html/2609.19169)

vllm-mlx
- MLX server with continuous batching and content-hash prefix/vision caches. M4 Max 128 GB, 4-bit: Qwen3-0.6B 525.5 tok/s, Qwen3-30B-A3B 109.7, Nemotron-30B-A3B 121.8 (llama.cpp 85.1); 1,642 tok/s aggregate at 16 concurrent on Qwen3-0.6B (3.7x; abstract says 4.3x). Runs/warm-up not stated. SiliconBench: unexplained 5-point fidelity drop and climbing memory. — [vllm-mlx, arXiv 2601.19139](https://arxiv.org/html/2601.19139); [SiliconBench](https://arxiv.org/html/2609.19169)

vllm-metal (vLLM project)
- v0.28.0 on 22 Sep 2026. vLLM scheduler + paged KV + chunked prefill on MLX/Metal, with a custom paged variable-length attention Metal kernel (packed sequences, no padding), prefix caching, batched MTP (Gemma 4 only, greedy), M5 Neural Accelerator prefill, pipeline parallelism across Macs. Eight ~6,000-token requests on Qwen3.6-35B-A3B 4-bit, uneven batch: 3.64 s vs 10.99 s (mlx_lm), 7.22 s (oMLX), 5.33 s (llama.cpp). MTP with one draft token on Gemma 4 E4B: +20% throughput at concurrency 1, +9% at 16 with 20% worse TTFT. SiliconBench: best concurrency scaling (3.65x chat, c=1 to 16), flat memory. — [vllm-metal blog](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0); [SiliconBench](https://arxiv.org/html/2609.19169)

oMLX
- Fork of vllm-mlx 0.1.0 on mlx-lm's BatchGenerator; block-based paged KV cache with a hot RAM tier and a cold SSD tier (safetensors, survives restart), copy-on-write prefix sharing, model pool with LRU, process memory limit (RAM minus 8 GB). Claims TTFT 30-90 s -> 1-3 s on long agent contexts; native GLM-5.2 kernels 845 vs ~29 tok/s on M3 Ultra. SiliconBench: passes all gates; best at concurrency 1 with SSD offload on Qwen3.8-27B; Qwen3.5-0.8B 113.4 tok/s at c=1 but only 212.6 at c=16. — [oMLX](https://github.com/jundot/omlx); [MLX discussion #3203](https://github.com/ml-explore/mlx/discussions/3203); [vllm-metal blog](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0); [SiliconBench](https://arxiv.org/html/2609.19169)

exo
- Distributed MLX with tensor parallelism over RDMA on Thunderbolt 5 (macOS 26.2+). Four M3 Ultra Mac Studios: Qwen3 235B 19.5 tok/s on one node, 31.9 on four (llama.cpp RPC fell from 20.4 to 15.2); Kimi K2 Thinking (1T) ~28-30 tok/s. SiliconBench, two M4 Pro 64 GB, Qwen3.5-35B-A3B 8-bit: single node EXO 66.8 tok/s vs mlx_lm 49.3 vs llama.cpp 40.0; two nodes 87.0 (1.30-1.37x). Apple: four M5 Ultra Mac Studios give "up to 3x" inference of one. Clusters stop at four Macs (no Thunderbolt switch). — [Jeff Geerling](https://jeffgeerling.com/blog/2025/15-tb-vram-on-mac-studio-rdma-over-thunderbolt-5); [SiliconBench](https://arxiv.org/html/2609.19169); [Apple newsroom Mac Studio](https://www.apple.com/my/newsroom/2026/08/apple-introduces-mac-studio-with-m5-max-and-m5-ultra/)

MLC-LLM
- In an M2 Ultra 192 GB study (Qwen-2.5, prompts up to 100k tokens): MLX had the highest sustained generation throughput; MLC-LLM had consistently lower TTFT at moderate prompts; llama.cpp efficient single-stream; Ollama trailed; PyTorch MPS memory-limited. — [arXiv 2511.05502, 9 Oct 2025](https://arxiv.org/abs/2511.05502)

Splash (Inco AI; first release 17 Sep 2026; Apache-2.0)
- Shared runtime/scheduler/cache with precompiled per-model Metal kernels; weights converted to kernel layouts at load; a trained "DFlash 2" draft model per model family for speculative decoding; INT8 KV cache by default; SSD prefix cache (32 GiB default); automatic batching; ANE + GPU prefill for the 27B; curated model list only; needs M3+, macOS 26.4, 36 GB. Vendor numbers on M5 Pro 48 GB (16-core GPU), SPEED-Bench coding prompts: Qwen3.6-35B-A3B 210 tok/s decode (1.7x next-fastest), prefill 2,011 tok/s at 32K, cached 32K TTFT 123 ms, 357 tok/s aggregate at 4 streams; Qwen3.8-27B 74 tok/s (2.0x), prefill 363 tok/s, 170 tok/s at 4 streams. Versus llama.cpp on the same GGUF: 35B-A3B 175 vs 69 (M5 Pro) and 209 vs 66 (M3 Max); 27B 74 vs 16 (27 with MTP). Next-token agreement with llama.cpp 97.8-99.5%. No energy figures. — [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md); [LM Studio blog](https://lmstudio.ai/blog/splash-engine)

uzu (Mirai), BaseRT, Magnitude, Locals, MTPLX, Lily, ds4
- uzu 0.7.4: Rust, own model format, Metal backend (third parties say layers can run as custom kernels or MPSGraph); headline 273 tok/s for a 9B model is on M5 Max with speculation, which is gated to M5 chips; on M1 Max it gives 55 tok/s plain (fastest single-stream non-speculative) but no concurrency scaling and broken code output from its distilled checkpoint. — [uzu](https://github.com/trymirai/uzu); [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)
- BaseRT (Base Compute): C++ straight on Metal, zero-allocation decode loop, dequantization fused in kernels, per-chip kernel selection, M5 tensor-op kernels for dense GEMM, MoE expert GEMM, fused MoE gate/up + SiLU and prefill attention. M5 Pro: prefill up to 6.4x llama.cpp and 3.9x MLX; decode 1.02-1.75x llama.cpp, 0.98-1.33x MLX. Single-request only. — [BaseRT](https://arxiv.org/html/2607.00501); [BaseRT M5](https://arxiv.org/html/2607.19438)
- Magnitude 0.2.12 (GGUF + DFlash drafter): M1 Max Qwen3.5-9B 41.6 tok/s plain; 82.6 tok/s on code with DFlash but slower than plain on long contexts (33.9 vs 37.5 at 27K). Locals 0.2.1 (MLX kernel tuning + batching scheduler): 60-63 tok/s single, 203 tok/s at 8 streams vs mlx-lm 69.7. — [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)
- MTPLX: native MTP on MLX, claims ~2.24x over non-MTP at temperature 0.6 on Qwen3.6-27B against its own baseline. Perplexity's "Lily" is named alongside uzu, MTPLX and Splash as a new Qwen-focused Mac engine; it does not run Qwen 3.8. — [MTPLX](https://github.com/youssofal/MTPLX) (snippet only); [Towards AI](https://pub.towardsai.net/three-mac-llm-engines-claim-to-be-the-fastest-splash-just-made-it-four-54e120d026ae) (snippet only)
- ANE-based: ANEMLL, ANEForge, NPUMoE (section 4). SSD-streaming: ds4, Hypura, MLX-Flash, AiiStream (section 5).

Cross-engine observations
- SiliconBench (M5 Pro 64 GB, nine stacks: llama.cpp, ollama, mlx_lm, vllm-metal, vllm-mlx, omlx, sglang-MLX, hf_transformers MPS, mistral.rs): only llama.cpp, vllm-metal and omlx pass completion + fidelity + model-coverage gates; authors conclude "the gaps lie in the inference engines, not the hardware". — [SiliconBench](https://arxiv.org/html/2609.19169); [NeurIPS poster](https://neurips.cc/virtual/2026/poster/139658)
- Speculative decoding helps short/code prompts and fades or reverses at long context on M1 Max (llama.cpp MTP +1 tok/s at 27K; Magnitude DFlash negative at 8K and 27K). — [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)

### Inferences
- What current engines leave unused, by resource (synthesis of the above): (1) CPU SME units — no shipping engine uses them alongside the GPU; only research prototypes do, and only for prefill. (2) ANE — only Splash (prefill FFN split) and possibly uzu via MPSGraph; nobody uses it during decode or for drafts in production. (3) M5 Neural Accelerators during decode — idle in every engine unless speculative verification batches use them (BaseRT lists this as future work). (4) DRAM bandwidth on Max/Ultra with quantized or MoE models — 25-55% unused per the section 2 arithmetic. (5) SSD — used for KV/prefix caches by oMLX, LM Studio, Splash; for weights only by niche projects. (6) Second Neural Engine on M6 — no engine mentions it.
- The fastest published MoE figure on a laptop-class chip is Splash's 210 tok/s for Qwen3.6-35B-A3B on M5 Pro, about 2x plain MLX (101.9) and BaseRT (110.7) on the same chip class; the difference is the draft model, not a faster kernel, since plain decode across engines is within ~10%.
- Exactness is a differentiator nobody leads on: Splash defaults to INT8 KV and reports 98-99.4% next-token agreement; SSD-streaming projects (AiiStream, llama.cpp RFC) advertise byte-identical output.

### Gaps
- Energy per token is not published by any of: llama.cpp, mlx-lm, LM Studio, Ollama, vllm-mlx, vllm-metal, oMLX, Splash, uzu, BaseRT. The only J/token figures are research (NPUMoE 52-137 mJ/token on ANE prefill).
- Splash's "next-fastest engine" is unnamed; Splash numbers are vendor-only (no independent M5 replication found). Splash 1.3.0 details came from secondary coverage.
- MLC-LLM's 2026 status and numbers: nothing newer than the Oct 2025 study was found. Lily and MTPLX primary pages were not read. "Strata" (named in Splash's README as a comparison engine) could not be identified.
- oMLX's benchmark page (omlx.ai/benchmarks) and the computingforgeeks Nov 2026 comparison could not be fetched.

## 9. Benchmarking practice for local inference on Macs in 2026, and criticisms

### Takeaway
The de facto conventions are llama-bench style pp/tg numbers (512-token prompt, 128 generated tokens, 30 s cool-down) and Apple's 4096-prompt / 128-token MLX runs; 2026 work argues these single-stream speed numbers mislead because they ignore memory headroom, output fidelity, concurrency, background load, synchronous-loop artefacts and energy. Energy is measured with `powermetrics` when it is measured at all, and vendor claims routinely mix hardware, quantization and speculative decoding.

### Cited Findings
- llama.cpp community standard: `llama-bench -p 512 -n 128 -ngl 99 --delay 30` on Llama 2 7B in F16 / Q8_0 / Q4_0; older chips pinned to a Nov 2023 commit for comparability, so rows across commits are not comparable (newer builds are ~30% faster on the same chip). — [llama.cpp discussion #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)
- Apple's MLX method: `mlx_lm.generate`, 4096-token prompt, 128 generated tokens, TTFT and generation tok/s. — [Apple ML Research](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)
- Research conventions: pp128-pp2048 and tg128 (BaseRT); two untimed warm-ups then three timed runs, greedy, fixed seed, 256 output tokens, powermetrics integrated over the run (Silicon Showdown); temperature 0, warm-up, 5 iterations, medians, prompt cache disabled, randomized IDs to defeat caching (lilting.ch). — [BaseRT](https://arxiv.org/html/2607.00501); [Silicon Showdown](https://arxiv.org/html/2605.00519v1); [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)
- SiliconBench (NeurIPS 2026; Penn State, UIUC, EXO Labs): three lenses — throughput/latency at concurrency 1/8/16 on chat and ~4K-token agent prompts, peak memory under contention with the OS, and fidelity as weighted F1 vs a vLLM A100 reference; a weekly maintainer agent re-runs it and caught an upstream bump that broke three of the stacks. "Speed-only leaderboards on Apple Silicon are misleading": the fastest stack may take memory the system needs or silently produce wrong output. — [NeurIPS poster](https://neurips.cc/virtual/2026/poster/139658); [arXiv 2609.19169](https://arxiv.org/html/2609.19169)
- Synchronous per-token timing loops report background interference as beneficial (6 of 8 light apps made decode "faster"); benchmarks should use pipelined loops; QoS demotion of background work makes it worse. — [The Gap Is the Loop](https://neurips.cc/virtual/2026/170048)
- Vendor-number criticisms: headline figures come from different machines (M4 Pro 48 GB, M5 Max 128 GB, M2 Max 96 GB); uzu's 273 tok/s needs M5-only speculation; Ollama's speculation cannot be disabled so "baseline" numbers include it; Ollama's 58 -> 112 tok/s compares different quantizations; vllm-mlx's abstract (4.3x, 21-87%) disagrees with its own tables (3.7x, 17%). — [lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark); [Ollama blog](https://ollama.com/blog/mlx); [vllm-mlx](https://arxiv.org/html/2601.19139)
- Energy reporting: Tom's Hardware reports task energy and energy-delay product for an agentic task rather than tok/s alone, noting a slower-decoding machine with faster prompt processing can finish sooner and use less energy. A community Apple-silicon benchmark repo retired its J/token figures after finding the battery gauge reports in 5% steps (identical runs differed 2x). GreenBench uses powermetrics and notes package power excludes DRAM and peripherals. — [Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/going-deep-on-local-ai-performance-with-apples-mac-studio-with-m5-ultra-inference-engine-recipes-mandatory-for-bigger-models-as-mlx-stack-matures); [apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench) (snippet only); [GreenBench](https://arxiv.org/abs/2608.28667)
- A community leaderboard notes a single run is one snapshot: thermal state, scheduler choices and background load all move the result. — [Anubis analysis](https://uncsoft.github.io/anubis-oss/analysis.html) (snippet only)
- Splash publishes next-token agreement against llama.cpp as a fidelity metric and uses SPEED-Bench coding prompts over HTTP. — [Splash README](https://raw.githubusercontent.com/incoai/splash/main/README.md)

### Inferences
- A defensible 2026 benchmark report on a Mac needs: same weights across engines; speculative decoding reported separately; cold and cached TTFT; long-context decode; concurrency; peak/wired memory; an output-fidelity check; wall or powermetrics energy with idle subtracted; power mode, AC state and cool-down stated; pipelined timing loop.
- Because package power omits DRAM, powermetrics-based J/token understates bandwidth-heavy decode relative to wall measurements; the two should not be mixed.

### Gaps
- No single community leaderboard with enforced methodology and energy was found; SiliconBench has no energy lens.
- No published benchmark controls for or reports Low Power / High Power Mode or battery state.
- Tom's Hardware's power methodology (wall meter vs software) could not be read.
