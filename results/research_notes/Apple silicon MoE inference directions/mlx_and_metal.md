# MLX and Metal as a platform for a high-performance LLM inference engine (state as of November 2026)

Research method note: web search and web fetch only (no code was run). GitHub release pages show day and month but no year; years below are inferred from the release order and from one tracker that dates v0.32.0 to 2026-07-07. Release-note items are PR titles as listed on the release pages, not verified against the diffs. Items marked "unconfirmed" could not be checked against a primary source.

## 1. MLX core releases through 2026 (0.26 to 0.32.4): Metal backend, eval / command buffers, memory, quantized matmul, fused attention, custom kernels, compile, CUDA, distributed, low-level APIs

### Takeaway
MLX's latest release is v0.32.4 (14 Oct 2026). Since v0.30.0 (Nov 2025) its Metal backend has a second kernel family ("NAX") that drives the M5 GPU Neural Accelerators through Metal 4 TensorOps, and 2026 added thread-local streams, multi-set residency handling, global-scale NVFP4, 1-bit affine, `gather_qqmm`, many head-size-specific fused attention kernels and zero-copy / foreign-buffer imports. The eval loop still commits a command buffer after 40 to 50 ops or 40 to 50 MB and blocks when more than 10 committed buffers are in flight or active memory exceeds the memory limit.

Command buffers and eval throttling (read from `main` source, Nov 2026)
- Per-command-buffer limits are chosen from the last letter of the GPU architecture name: `p` (phone) 20 ops / 40 MB; `g` (base and Pro) 40 ops / 40 MB; `s` (Max) and `d` (Ultra) 50 ops / 50 MB; default 40 / 40. The commit test is `(buffer_ops_ > max_ops) || ((buffer_sizes_ >> 20) > max_mb)`, and both limits can be overridden through `env::max_ops_per_buffer` / `env::max_mb_per_buffer`. The architecture string can be overridden with `MLX_METAL_GPU_ARCH`. — [mlx/backend/metal/device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp)
- The user-facing env vars are `MLX_MAX_OPS_PER_BUFFER` and `MLX_MAX_MB_PER_BUFFER`; a maintainer suggested `MLX_MAX_OPS_PER_BUFFER=1` as a workaround for GPU "Internal Error" timeouts, noting it may slow things down. — [mlx issue #1231 (mirror)](https://upd.dev/ml-explore/mlx/issues/1231); a later report says neither `MLX_MAX_OPS_PER_BUFFER=1` nor `MLX_MAX_MB_PER_BUFFER=10` prevents the macOS GPU watchdog killing LoRA training while the display is active — [mlx issue #3267 (mirror)](https://upd.dev/ml-explore/mlx/issues/3267)
- Command buffers are created with `commandBufferWithUnretainedReferences`; MLX keeps the input buffers alive itself by moving a set of data pointers into the completion handler / commit callback. — [device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp), [mlx/backend/metal/eval.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/eval.cpp)
- Throttle: `static constexpr int MAX_ACTIVE_TASKS = 10;`. After every primitive eval, `scheduler::wait_for_capacity(open_streams)` returns immediately only if `n <= MAX_ACTIVE_TASKS && !(n > 0 && over_memory_limit())`, where `over_memory_limit` is `get_active_memory() > get_memory_limit()`. Otherwise it first finalizes (commits) every open GPU stream, then waits on the atomic task counter until a committed buffer completes, repeating while over the memory limit. A "task" is one committed command buffer (`notify_new_task` on commit, `notify_task_completion` in the completion callback). — [mlx/scheduler.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/scheduler.cpp), [mlx/scheduler.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/scheduler.h), [eval.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/eval.cpp)
- Graph order: a DFS pass computes degrees, then the tape is built breadth-first with a width limit `MLX_BFS_MAX_WIDTH` (default 20); work is popped from the end of the tape so inputs run first. `async_eval` calls the same `eval_impl` with `async=true`, attaches an event to each output and returns without waiting; it is not allowed inside a graph transformation. — [mlx/transforms.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/transforms.cpp)
- Cross-encoder ordering uses Metal fences (`newFence`, `updateFence`, wait on fences of earlier encoders that produced the inputs), `encodeSignalEvent` / `encodeWait` for events, and `memoryBarrier(BarrierScopeBuffers)` when an input was a previous output in the same encoder. On a failed command buffer the handler poisons and manually signals events so waiters do not hang. — [device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp)
- Metal language version selected at run time: macOS/iOS 27+ uses raw value `(4 << 16) + 1` (Metal 4.1, with a TODO to use `LanguageVersion4_1`); macOS/iOS 26 uses 4.0; macOS 15 / iOS 18 uses 3.2; otherwise 3.1. — [device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp)
- NAX detection: disabled if built with `MLX_METAL_NO_NAX`; otherwise requires `__builtin_available(macOS 26.2, iOS 26.2, tvOS 26.2, visionOS 26.2, *)` and GPU generation `>= 17` (or `>= 18` for phone-class `p` architectures). — [device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp)

Memory management (read from `main` source)
- Memory limit default: `block_limit_ = min(1.5 * max_recommended_working_set_size, 0.95 * memory_size)`. GC threshold: `gc_limit_ = min(0.95 * max_rec_size, block_limit_)`. Cache limit default equals the memory limit (`max_pool_size_ = block_limit_`). `set_cache_limit` does not trim immediately; trimming happens on the next malloc/free. — [mlx/backend/metal/allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- All MLX buffers are `MTLResourceStorageModeShared | MTLResourceHazardTrackingModeUntracked`. Sizes above one page are rounded up to the VM page size. Small allocations (below `small_size_`, value not shown in the fetched excerpt) come from one `MTLHeap` unless the device is "Apple Paravirtual device". — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- GC runs only on a cache miss, when `active + cache + size >= gc_limit_` or when the buffer count reaches the device `resource_limit`; exceeding the count after GC throws "[metal::malloc] Resource limit (N) exceeded." — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- External (user) memory: `make_buffer` wraps a caller pointer with `device_->newBuffer(ptr, size, resource_options, nullptr)` (no copy). The source comment says: "The caller owns this memory, so it is not wired. Wiring a file-backed mapping would read the whole file...". Such buffers count toward active memory and resource count but are not added to a residency set and are not cached on release. — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- Residency sets (macOS 15 / iOS 18+, Metal 3 family): the wired limit is the set capacity; `insert` skips a buffer if `total_wired_ + bytes > capacity_` (it stays tracked but unwired); `resize` adds or removes buffers to fit. Since 2026 MLX splits wired buffers across several sets: `MLX_RESIDENCY_SET_MAX_PCT` (default 5) caps each set at that percentage of `recommendedMaxWorkingSetSize`, floored at 64 MiB; `requestResidency()` is called once when a set is created and `commit()` on every insert/erase/resize. `MLX_METAL_RESIDENCY_REFRESH_INTERVAL_MS` (default 0 = off) starts a thread that re-requests residency for every non-empty set; the code comment says macOS can drop residency after GPU idle. `MLX_RESIDENCY_DEBUG` logs new sets. New sets are attached to the queue (`addResidencySets`) before each commit because "Metal locks a command buffer's residency at commit time". — [mlx/backend/metal/resident.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/resident.cpp), [device.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/device.cpp)
- `mx.set_wired_limit` docs (v0.32.4): only useful on macOS 15.0+; default `0`; "should remain strictly less than the total memory size"; setting above the system wired limit is an error; raise the system limit with `sudo sysctl iogpu.wired_limit_mb=<MB>`; `device_info()["max_recommended_working_set_size"]` is described as the system wired limit. — [mlx set_wired_limit docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html)

Quantized matmul
- `mx.quantize` (v0.32.4 docs): `affine` mode supports group sizes 32, 64 (default), 128 and bits 1, 2, 3, 4 (default), 5, 6, 8, with scale and bias; `mxfp4` (group 32, 4-bit E2M1, E8M0 scale), `mxfp8` (group 32, 8-bit E4M3, E8M0 scale), `nvfp4` (group 16, E2M1, E4M3 scale, optional float32 `global_scale`); no bias for the fp modes. Affine values are packed into uint32 from low to high bits. Input must be at least 2-D with last dim divisible by the group size. — [mlx quantize docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html)
- `gather_qmm` takes an optional `sorted_indices` flag that "may allow a faster implementation". — [mlx gather_qmm docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.gather_qmm.html)
- On the NAX path `gather_qmm_rhs_nax` hard-coded a 64-row block (`bm = 64`, with a TODO); the kernel walks sorted indices inside a tile and reruns its full K loop once per distinct expert in the tile (see section 3 for numbers). The non-NAX path uses block size 16. — [mlx issue #3925](https://github.com/ml-explore/mlx/issues/3925)

Fused attention
- `mx.fast.scaled_dot_product_attention(q, k, v, *, scale, mask=None, sinks=None, force_fused=False, stream=None)`: mask is `"causal"` (lower-right aligned) or a boolean/additive array of at most 4 dims; softmax is computed in float32 regardless of input precision; GQA/MQA should pass un-tiled k and v; `force_fused=True` raises if no fused kernel exists and "may select a slower kernel in some configurations, but can reduce memory use". — [mlx SDPA docs v0.32.4](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.fast.scaled_dot_product_attention.html)
- Head sizes with dedicated fused kernels added in 2026 (from PR titles): 96 full attention (#3943), 256 full attention on NAX (#3842, #4416 with array mask), D512 vector attention (#4459), D96/V64 (#4499), D72/D80 long unmasked on NAX (#4455). No VJP for mask or sinks (#2909, v0.30.x); SDPA VJP added in v0.32.4 (#4563). — [MLX releases](https://github.com/ml-explore/mlx/releases), [MLX releases p2](https://github.com/ml-explore/mlx/releases?page=2)

Custom Metal kernels
- Signature (v0.32.4): `metal_kernel(name, input_names, output_names, source, header='', ensure_row_contiguous=True, atomic_outputs=False, compile_options=None)`; `compile_options` currently documents only `"math_mode"`: `"safe"` (default, keeps IEEE behaviour such as `exp(-inf) == 0`), `"relaxed"`, `"fast"`. Call-time args: `inputs`, `template` (Dtype / int / bool), `grid`, `threadgroup`, `output_shapes`, `output_dtypes`, `init_value`, `verbose`. — [mlx metal_kernel docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.fast.metal_kernel.html), [custom Metal kernels guide](https://ml-explore.github.io/mlx/build/html/dev/custom_metal_kernels.html)
- Only the body is supplied; the signature is generated. Multiple outputs are supported. Any attribute from MSL spec Table 5.8 used in the source becomes an argument. `<name>_shape/_strides/_ndim` are injected when referenced. `grid` is passed to `dispatchThreads`. `init_value` pre-fills all outputs so a kernel can update only part of an output; `atomic_outputs=True` makes all outputs `device atomic<T>`. Each new kernel object builds a Metal library (JIT) so kernels should be created once and reused. Gradients need `@mx.custom_function` with a hand-written VJP. — [custom Metal kernels guide](https://ml-explore.github.io/mlx/build/html/dev/custom_metal_kernels.html)
- The guide does not document threadgroup (shared) memory declarations, in-place writes to inputs, or maximum grid / threadgroup sizes. — [custom Metal kernels guide](https://ml-explore.github.io/mlx/build/html/dev/custom_metal_kernels.html)

CUDA and distributed
- CUDA: first PyPI release in v0.27.1 (Jul 2025); quantized matmul family (QMM, GatherQMM, 3/5/6-bit, fp quantizations) arrived in v0.31.0 to v0.31.2; consumer GPU support (#3056) and "dense MoE support" in v0.30.x; v0.32.4 adds `fp_gather_qmv` and `gather_qmm_rhs_sm80`. — [MLX releases](https://github.com/ml-explore/mlx/releases), [p2](https://github.com/ml-explore/mlx/releases?page=2), [p3](https://github.com/ml-explore/mlx/releases?page=3)
- Distributed: JACCL backend gives RDMA over Thunderbolt 5 (macOS 26.2+, faster on 26.3+); Apple demonstrated two M5 Max machines and a four-Mac-Studio cluster running a 1-trillion-parameter model via LM Studio at WWDC 2026. — [MLX releases p2](https://github.com/ml-explore/mlx/releases?page=2), [WWDC26 session 382](https://developer.apple.com/videos/play/wwdc2026/382/)

### Inferences
- The "about 10 in-flight buffers" throttle seen by engine authors is exactly `MAX_ACTIVE_TASKS = 10` committed command buffers; because `wait_for_capacity` now commits open streams before waiting (#4556 in v0.32.4), any step that must stay inside one command buffer has to fit the per-buffer op/MB limits or raise them through the two env vars before `import mlx`.
- Because MLX deliberately does not wire user/no-copy buffers and command buffers use unretained references, an engine that maps expert weights from a file must manage their residency (mlock or its own residency set) and lifetime itself.
- The default cache limit equal to the memory limit (up to 1.5x the recommended working set) explains reports of cache-driven memory growth; setting an explicit cache limit is necessary on small-RAM Macs.
- The per-set cap (default 5% of the working set, max 32 sets per queue per Apple docs) suggests MLX hit a driver cost that scales with residency-set size; this is not stated in the source.

## 2. mlx-lm through 2026: caches, speculative decoding, batching, MoE layers, servers built on it

### Takeaway
mlx-lm's latest release is v0.32.2 (16 Oct 2026). It has a batched generator with batch-aware cache classes, an LRU / trie prompt cache in the server, safetensors prompt-cache files, 8-bit default quantized KV cache and speculative decoding, but its MoE path is still a Python-level sort, `gather_qmm`, unsort around generic kernels, and third-party servers (vllm-mlx, oMLX) add paged or SSD-tiered KV caches on top.

### Cited Findings
- Release timeline (years inferred): v0.30.4 (19 Jan 2026) continuous-batching server benchmark (#728), compiled SwiGLU (#753), tensor sharding for GPT-OSS / MiniMax / LongCat; v0.30.6 (4 Feb 2026) distributed inference in the server (#741), `BatchRotatingKVCache` default in batch mode (#834); v0.31.0 (7 Mar 2026) `--prefill-step-size` flag (#943), `mx.clear_cache()` in piecewise prompt processing (#917), `cached_tokens` in usage (#849), better server caching (#911); v0.31.2 (7 Apr 2026) Gemma 4 (#1093), `LRUPromptCache` refactor (#1019), batch generator refactor (#1072), presence/frequency penalties (#971), speculative-decoding output-corruption fix (#1109), bring back `max-kv-size` in batch generator (#1106); v0.31.3 (22 Apr 2026) thread-local generation stream (#1090); v0.32.0 (15 Oct 2026) "Global scale for NVFP4 quantized MoEs" (#1844), Hadamard-rotated 2-bit Qwen3.5 (#1941), unconverted model support (#1962). — [mlx-lm releases](https://github.com/ml-explore/mlx-lm/releases)
- Cache classes on `main`: `ConcatenateKVCache`; `KVCache` (preallocates in `step = 256` token slots); `QuantizedKVCache` (defaults `group_size=64`, `bits=8`; `KVCache.to_quantized(group_size=64, bits=4)`); `RotatingKVCache(max_size, keep=0)` (cannot be quantized; trimmable only while `offset < max_size`); `ArraysCache` (not trimmable); `ChunkedKVCache`; `CacheList`; `BatchKVCache` (left-padded, `merge` / `extract` / `extend` / `filter`); `BatchRotatingKVCache`. `make_prompt_cache(model, max_kv_size)` uses `RotatingKVCache(max_size=max_kv_size, keep=4)` when a size is given. `save_prompt_cache` / `load_prompt_cache` write and read `.safetensors`; `trim_prompt_cache` trims only if every layer cache is trimmable. — [mlx_lm/models/cache.py](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/cache.py)
- A user on a 24 GB machine (27B model, 64k context) blamed kernel panics on the `step=256` KV reallocation loop and proposed `--kv-preallocate-size` (PR #1920, Sep 2026; not shown as merged). — [mlx-lm issue #883](https://github.com/ml-explore/mlx-lm/issues/883)
- MoE implementation: SwitchGLU passes a broadcast input for gate and up projections (one activation shared across a token's k expert slots) and a per-slot input for down. — [arXiv 2610.31479](https://arxiv.org/pdf/2610.31479) (as summarized by search; the paper was not read in full). A Rust crate that describes itself as a 1:1 port of `switch_layers.py` applies a sort-then-unsort around the kernel. — [mlxrs switch.rs](https://docs.rs/crate/mlxrs/0.1.0/source/src/lm/nn/switch.rs)
- A profiling write-up on Qwen3.6-35B-A3B (M3 Max) found `gather_mm` rebuilt identity row indices "hundreds of times per decoded token" and the eval walk did several `unordered_map` operations per graph edge; fixing both gave +2.0 to 2.8% decode and +3.6% prefill at 8K (PR #3920). — [mlx issue #3957](https://github.com/ml-explore/mlx/issues/3957)
- A community fork adds a fused SwiGLU + `gather_qmv` kernel to cut launch overhead in the MoE expert path; it is not upstream. — [benjamin-levin/mlx fork](https://github.com/benjamin-levin/mlx) (unconfirmed details; seen in search summary only)
- vllm-mlx (paper Jan 2026, M4 Max): continuous batching scaling to 4.3x aggregate throughput at 16 concurrent requests, 21% to 87% higher throughput than llama.cpp on text models, a "Simple Engine" for one user and a "Batched Engine"; docs describe a paged KV cache. — [arXiv 2601.19139](https://arxiv.org/html/2601.19139), [vllm-mlx docs](https://docsearch.algolia.com/mcp/docs/repo/waybarrios/vllm-mlx)
- oMLX: two-tier KV cache, hot tier in RAM and cold tier on SSD in safetensors blocks restored on a matching prefix even after a restart; batching runs through mlx-lm's `BatchGenerator`. — [jundot/omlx](https://github.com/jundot/omlx), [Better Stack guide](https://betterstack.com/community/guides/ai/omlx-apple-silicon/)
- Apple stated at WWDC 2026 that Ollama, LM Studio and vLLM use MLX on the Mac and that LM Studio's "MLX Distributed" support "is coming later this year". — [WWDC26 session 382](https://developer.apple.com/videos/play/wwdc2026/382/)
- Speculative decoding on Apple silicon: a NeurIPS 2026 workshop paper reports that every speculative-decoding method it evaluated lowered throughput on Apple hardware under its single-request benchmark, while KV-cache pruning gave up to 1.75x and transferable ported-kernel ideas up to 1.20x decode. — [arXiv 2610.31479](https://arxiv.org/abs/2610.31479)
- ExecuTorch's MLX delegate (PyTorch blog, updated 15 May 2026, experimental) runs sparse MoE (Qwen 3.5 35B-A3B, 256 experts, top-8) through "custom gather operations" on MLX kernels and supports BF16/FP16/FP32, 2/4/8-bit affine and NVFP4. — [PyTorch blog](https://pytorch.org/blog/running-pytorch-models-on-apple-silicon-gpus-with-the-executorch-mlx-delegate/)

### Inferences
- mlx-lm has no MoE-specific scheduling (no expert-grouped tiles, no fused gate/up/SiLU, no expert residency management); the gains reported by BaseRT and the community PRs come from exactly those places.
- Structured output is not part of mlx-lm core in the fetched release notes (only logits processors, tool-call parsers); constrained decoding appears to be left to servers on top.
- Prompt-cache persistence in mlx-lm is whole-file safetensors; block-level SSD tiering exists only in third-party servers (oMLX).

### Gaps
- `mlx_lm/models/switch_layers.py` returned 404 at the expected path on `main` (the file may have moved); the sort threshold and exact op calls could not be quoted from the primary source.
- No documentation was found for LM Studio's `mlx-engine` batching or cache design, or for mlx-omni; no 2026 head-to-head of vllm-mlx / oMLX / LM Studio / mlx-lm server.
- mlx-swift release notes were not reviewed; the only confirmed facts are that NAX kernels were made JIT-compilable for MLX Swift (v0.30.1) and that the Metal backend is on by default on iOS since v0.32.0.

## 3. Known MLX performance pitfalls and issues (MoE, memory, wired memory, compiler, chip generations)

### Takeaway
The best-documented MoE pitfall is tile waste in `gather_qmm` at short per-expert runs (only about 21% of the fp16 ceiling at 16 rows per expert on M5); the most serious stability issues are kernel panics and false "Insufficient Memory" errors tied to wired memory and the Apple GPU driver, plus an Xcode 26.5 Metal compiler bug that silently mis-compiled quantized matmul kernels.

### Cited Findings
- `gather_qmm_rhs_nax` tile waste (base M5, 10 GPU cores, macOS 26, E=256, K=2048, N=512, 4-bit affine group 64; ceiling 15.4 TFLOPS fp16 on the Neural Accelerator path): 4 rows/expert 5.3% of ceiling, 8 rows 10.4%, 16 rows 20.8%, 32 rows 42.0%, 64 rows 77.9%, 256 rows 87.2%; useful arithmetic is roughly `min(1, rows_per_expert / BM)`. Aligned runs reached 11.94 TFLOPS versus 6.85 TFLOPS for runs shifted across tile boundaries; skewed run lengths did worse than uniform (16.9% vs 20.8%). Rows per expert = tokens_per_step x top_k / num_experts (about 16 for 256 experts, top-8, 512-token chunks). A BM=32 variant gave about 1.3 to 1.45x at 16 rows/expert and 1.066x end-to-end TTFT on Qwen3.6-35B-A3B 4-bit at 32k tokens (62.8 s to 58.9 s); each extra BM instantiation adds about 108 kernels to the metallib. Maintainer reply (2 Aug 2026): PRs tuning block sizes are welcome; issue closed. — [mlx issue #3925](https://github.com/ml-explore/mlx/issues/3925)
- Three community perf PRs (31 Jul 2026, M3 Max, Qwen3.6-35B-A3B): #3918 picks the `gather_qmm_rhs` tile by rows per expert (16x32 below 32 rows, 32x64 from 32 up; +12 to 22% kernel, +6.2% MoE prefill at 32K; kernel reaches 96% of an equivalent dense qmm); #3919 fuses the causal mask into the softmax in the SDPA ops fallback (the old path materialized about 512 MB of masked scores per layer chunk at 32K; mask+softmax stage -45%, +2.8% prefill); #3920 as in section 2. The issue was converted to Discussion #4031; merge status not shown. — [mlx issue #3957](https://github.com/ml-explore/mlx/issues/3957)
- v0.32.2 and v0.32.3 release notes list "skipped simdgroup work for quantized MoE on NAX" (#4352), "sorted gather_qmm on ragged K" (#4009) and "gather_mm and gather_qmm Metal improvements" (#4567, #4572), so part of this was addressed upstream. — [MLX releases](https://github.com/ml-explore/mlx/releases)
- MoE correctness reports: garbage output from quantized Gemma 4 26B-A4B (128 experts, top-8) on a base M4 (10 GPU cores) while the same files work on M3 Ultra; a 64-expert Qwen3 30B-A3B did not fail; merged into #3384 without a stated root cause (Apr 2026, MLX 0.31.1). — [mlx issue #3393](https://github.com/ml-explore/mlx/issues/3393). - Xcode 26.5 (Metal compiler `metalfe-32023.883`) mis-compiled the NAX GEMM / `qmm` / `qmm_splitk` kernels: locally built MLX produced garbage for quantized models (narrowed to 6-bit `quantized_matmul(transpose=True)` at M=720, K=N=2048). - A roughly 10x `SwitchGLU` slowdown was reported to depend on an unrelated environment factor (many YAML files opened at import). — [mlx issue #2583 (mirror)](https://upd.dev/ml-explore/mlx/issues/2583)

### Inferences
- For MoE prefill, the efficiency of any tile-based expert kernel is governed by rows per expert relative to tile height; with 256 experts and top-8 routing, chunks under about 2048 tokens leave most Neural Accelerator arithmetic wasted unless the tile is chosen per run or experts are batched across chunk boundaries.
- Shipping a prebuilt metallib (or pinning the deployment target) is safer than compiling kernels with whatever Xcode the user has; a self-check of quantized matmul outputs at start-up would catch a compiler regression of the #3586 kind.
- Wiring close to the recommended working set on a machine also running other GPU clients is a panic risk on macOS 26.x; a conservative wired limit and a hard memory limit are prudent.

### Gaps
- Root cause of #3384 / #3393 (Gemma 4 on base M4) and of the M5 Pro false OOM was not found.
- Merge status of PRs #3918 to #3920 and of the BM=32 change is unknown.
- No primary report was found on "slowdowns from the buffer cache" specifically; evidence is limited to the allocator source.

## 4. Metal 4 and later: ML encoder, tensors in shaders, Metal Performance Primitives, Neural Accelerators, OS and chip requirements

### Takeaway
Metal 4 (WWDC 2025, OS 26, Apple M1 / A14 and later) added `MTLTensor`, an ML command encoder and in-shader TensorOps (`matmul2d`, convolution) through Metal Performance Primitives; on M5 / A19 GPUs these run on a dedicated matrix-multiply block in every shader core ("Neural Accelerators"), giving 4 to 8x GEMM, and OS 27 (WWDC 2026) extends TensorOps to fp8 / fp4 / 2-bit types, MX block scales as auxiliary tensor planes and cooperative tensors as matmul inputs.

### Cited Findings
- Metal 4 core API: `MTL4CommandQueue`, `MTL4CommandBuffer` (requested from the device, encodable in parallel), `MTL4CommandAllocator` (direct control of command-buffer memory), one unified compute encoder (dispatch, blit, acceleration structures), `MTL4ArgumentTable`, explicit barriers, residency sets that must contain every resource a committed command buffer needs, placement sparse buffers/textures backed by placement heaps, and a separate `MTL4Compiler`. Supported on Apple M1 and later and A14 Bionic and later. — [WWDC25 session 205 "Discover Metal 4"](https://developer.apple.com/videos/play/wwdc2025/205/)
- `MTL4MachineLearningCommandEncoder` runs whole networks in the command stream from a Metal ML package (`MTLPackage`, produced from a Core ML model by `metal-package-builder`); inputs and outputs are `MTLTensor`s; tensor usage flags are `MTLTensorUsageMachineLearning`, `MTLTensorUsageCompute`, `MTLTensorUsageRender`; tensors can be created from a device or a buffer, and device-created tensors "offer the best performance". — [WWDC25 session 262](https://developer.apple.com/videos/play/wwdc2025/262/), [Machine learning passes docs](https://developer.apple.com/documentation/metal/machine-learning-passes)
- Neural Accelerators: dedicated matrix multiply-accumulate (C = A x B + C) hardware inside each GPU shader core on M5 and A19 GPUs, scaling with core count; Apple's claims are GEMM 4 to 8x faster depending on precision, LLM time-to-first-token up to 4x, token generation up to 25%. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- Apple demo, 4K x 4K matmul: simdgroup_matrix kernel over 2 s with 0% Neural Accelerator utilization; TensorOps over 0.5 s (over 4x) at over 50% utilization; TensorOps plus Morton-order threadgroup dispatch about 0.33 s (about 7x) at near 100%. Apple's advice: authors using the SIMD-group matrix API should move to TensorOps. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- TensorOps API shape: host `metal::tensor` handles or in-kernel `tensor_inline` over a raw buffer pointer; `slice` per threadgroup; `matmul2d_descriptor(TILEM, TILEN, dynamic_length_v<int>, transposeLeft, transposeRight)`; `matmul2d<descriptor, execution_simdgroups<4>> op; op.run(tA, tB, tC)`. Cooperative tensors keep the result in thread-private storage spread across the participating threads so an activation can be applied before one `store`. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/), [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/)
- Performance guidance from Apple: template the tile sizes; larger threadgroup M/N tiles improve reuse but oversized SIMD-group tiles spill registers; tile K explicitly and insert `threadgroup_barrier` every few K tiles to keep SIMD groups in step; dispatch tiles along a Morton or Hilbert curve; large matrices are compute bound, skinny (single-token decode) are bandwidth bound; profile with Metal System Trace ("Neural Accelerator Utilization" counter in the Performance Limiters set) and the Xcode Metal debugger. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- Data types by OS, per the tech talk: FP16; BFloat16 tensors added in OS 26.1; cooperative tensors as matmul inputs (custom dequantization inside kernels) in OS 26.3; 4-bit and 8-bit integer tensors in OS 26.4. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- WWDC 2026 session 330 states the timeline differently: OS 26 added native 4-bit and 8-bit integer types; OS 27 adds 4-bit and 8-bit floating-point types (`MTLTensorDataTypeMetalFloat8E4M3`), 2-bit integers, MX scaling formats with FP8 E8M0 block scales (`MTLTensorDataTypeMetalFloat8UE8M0`), multi-plane tensors (`MTLTensorAuxiliaryPlaneDescriptor`, `MTLTensorPlaneTypeScales`, `blockFactors` such as 32x1), MSL aliases such as `tensor_blockwise<tensor_plane_scales, device metal_fp8_ue8m0_format, 32, 1>`, and cooperative tensors reusable directly as inputs to a second matmul ("new in macOS/iOS 27"), with helpers `get_destination_cooperative_tensor`, `reduce_rows`, `map_iterator`, `is_compatible_as_left_input` / `is_compatible_as_right_input`, `get_left_input_cooperative_tensor`. The session builds FlashAttention this way (QK^T into a cooperative tensor, row max, exp, multiply by V) using `execution_simdgroup` scope. — [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/); the two Apple sources conflict on whether cooperative-tensor matmul inputs arrived in 26.3 or 27 — [tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- Session 330 guidance: pass quantized tensors straight into TensorOps so dequantization is handled and hardware acceleration is used automatically; for custom formats dequantize into a cooperative tensor rather than threadgroup memory; the new small types "have additional alignment requirements". — [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/)
- Apple's MPP Programming Guide (Version 1, dated 2026-03-16 per search result) documents `matmul2d` GEMM, `matmul2d_descriptor(SM, SN)` and execution scopes. — [MPP Programming Guide PDF](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)
- Constraints reported by engine authors: kernels must be compiled with `-std=metal4.0` (BaseRT); matmul descriptor dimensions must be multiples of 16 or the f16 tensor probe fails (llama.cpp PR #21048, macOS 26.4, M5 MacBook Air); creating a tensor-op pipeline state takes about 1 to 2 s each (comment in the llama.cpp PR thread); on M2 Ultra bfloat tensor kernels compiled but `maxTotalThreadsPerThreadgroup` reported 0; some macOS 26 betas shipped MPP headers without `bfloat`. — [arXiv 2607.19438](https://arxiv.org/html/2607.19438), [llama.cpp PR #16634](https://github.com/ggml-org/llama.cpp/pull/16634)
- On chips without Neural Accelerators TensorOps runs "optimized shader implementations" (same code M1 to M5). Measured on M4 Max by an independent preprint (11 Jun 2026): `matmul2d` runs on the ordinary shader cores (no dedicated datapath, no Neural Engine routing), fp8 E4M3 is emulated at about 0.94x fp16 throughput, accumulation is at least fp32, the cooperative tensor is an undocumented 8x8 fragment layout, and a hand-fused GEMM + bias + GELU kernel beats the decomposed path by 6.5 to 12.9% when cache-resident. llama.cpp found the tensor path slightly slower than its simdgroup kernel on M2 Ultra and enables it only on M5 and later. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/), [arXiv 2606.12765 "Rigel"](https://arxiv.org/abs/2606.12765), [llama.cpp PR #16634](https://github.com/ggml-org/llama.cpp/pull/16634)
- BaseRT (arXiv, 21 Jul 2026; M5 Pro 48 GB; baselines llama.cpp b9960, mlx-lm 0.31.3 + MLX 0.32.0): hand-written Metal 4 tensor kernels for dense 4/8-bit GEMM (reading packed weights directly from device memory; "threadgroup-memory staging isn't necessary for peak GEMM"), MoE expert GEMM over routed tokens, a fused MoE gate/up projection with SiLU applied on the accumulators in one dispatch, and flash-attention prefill with exact online softmax; decode stays on GEMV kernels because it is bandwidth bound. Results: prefill up to 6.4x llama.cpp and 3.9x MLX (peak on Qwen3-30B-A3B at pp128); decode 0.98 to 1.33x MLX. Qwen3.6-35B-A3B 4-bit: decode 110.7 tok/s (MLX 101.9, llama.cpp 63.1), pp2048 2,788 tok/s (MLX 2,426, llama.cpp 1,628). — [arXiv 2607.19438](https://arxiv.org/html/2607.19438)
- MLX on M5 (Apple ML Research, 19 Nov 2025; MacBook Pro M5 24 GB vs M4; 4096-token prompt, 128 generated): TTFT speedups 3.3 to 4.1x (Qwen3-30B-A3B 4-bit 3.52x; gpt-oss-20b MXFP4-Q4 3.33x; Qwen3-14B 4-bit 4.06x), generation 1.19 to 1.27x, attributed to memory bandwidth 153 GB/s vs 120 GB/s. — [Apple ML Research](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)

### Inferences
- "Matrix units exposed to shaders" exist only on M5 / A19-class GPUs; on M1 to M4 the same TensorOps source compiles to ordinary shader code and offers no speedup over a good simdgroup kernel, so a pre-M5 engine gains nothing from the tensor path except portability.
- Native int4/int8 (OS 26.4) and fp4/fp8/2-bit with block scales (OS 27) mean dequantization can be done by the accelerator path itself on M5; MLX's affine format (uint32-packed, per-group scale and bias) does not obviously map to Apple's MX-style scale planes, so custom dequantization into cooperative tensors is the likely route for affine weights.
- The fused gate/up + SiLU MoE kernel and per-run tile choice are the two published MoE-specific wins over MLX on M5; neither depends on M5-only features in principle, but the measured gains are M5-only.

## 5. Metal memory behaviours: working-set limits, wiring, no-copy buffers, residency sets, command-buffer retention

### Takeaway
Residency sets are a request, not a guarantee, and they are capped at 32 per queue or command buffer; no-copy buffers need a page-aligned pointer and length within a single VM region and are not wired by MLX; the system wired limit is the undocumented `iogpu.wired_limit_mb` sysctl (0 = system default), and several driver-level bugs around wired GPU memory were open in 2026.

### Cited Findings
- Residency sets: allocations (`MTLBuffer`, `MTLTexture`, `MTLHeap`) are added then applied with `commit()`; adding any allocation that comes from a heap makes the entire heap resident; each command buffer and each command queue can hold up to 32 residency sets; Metal attaches the queue's sets to a command buffer at `commit()`; `requestResidency()` does the CPU work ahead of the first commit but "may postpone some of the necessary steps ... where other apps have competing memory needs"; `endResidency()` lets Metal reuse the memory. Without residency sets, per-encoder `useResource` calls cost CPU and Metal makes resources resident right after commit, delaying GPU start. — [Apple: Simplifying GPU resource management with residency sets](https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets)
- `makeBuffer(bytesNoCopy:length:options:deallocator:)`: pointer must be page-aligned, length must give a page-aligned region, and "the existing memory allocation needs to exist within a single virtual memory (VM) region". Nothing is documented about wiring. — [Apple makeBuffer(bytesNoCopy:) docs](https://developer.apple.com/documentation/metal/mtldevice/makebuffer(bytesnocopy:length:options:deallocator:))
- MLX leaves no-copy user buffers out of its residency sets because "Wiring a file-backed mapping would read the whole file". — [mlx allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- MLX's residency code notes that macOS can drop residency after GPU idle and offers a periodic re-request thread (off by default). — [mlx resident.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/resident.cpp)
- Residency-set leak (FB23959296, Jul 2026, macOS 26.5.2): if a process makes a buffer resident and tears everything down without ever doing GPU work, the memory (4 GB in the repro, about 16 GB in llama.cpp issue #25937) is not returned; any dummy GPU command at any point in the process fixes it. No Apple reply. — [Apple Developer Forums 839089](https://developer.apple.com/forums/thread/839089)
- System limit: `iogpu.wired_limit_mb` (older systems: `debug.iogpu.wired_limit`); 0 means the system default; undocumented by Apple; commonly reported default is about 75% of RAM as the Metal ceiling; resets on reboot. — [mlx set_wired_limit docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html), [devnote on the macOS Metal VRAM cap](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap) (secondary), [Apple Developer Forums 732035](https://developer.apple.com/forums/thread/732035)
- A user report says that even with the limit set to 124 GB usage capped around 64 GB in LM Studio. — [LM Studio bug tracker #651](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/651) (anecdotal)
- Apple documents `MTLCommandBufferError.outOfMemory` as the GPU lacking enough memory to run a command buffer; the same "Insufficient Memory (00000008:kIOGPUCommandBufferCallbackErrorOutOfMemory)" string appears for working sets under 2 GB on M5 Pro / macOS 26.5. — [Apple Developer Forums 827607](https://developer.apple.com/forums/thread/827607)
- Kernel panic signature tied to wired GPU memory: "completeMemory() prepare count underflow" at IOGPUMemory.cpp:550 (macOS 26.3 to 26.4). — [mlx-lm issue #883](https://github.com/ml-explore/mlx-lm/issues/883)
- llama.cpp exposes `GGML_METAL_NO_RESIDENCY=1`; one downstream report says it reduced a hang rate from about 30 to 50% to about 10%. — [node-llama-cpp issue #595](https://github.ddaodan.workers.dev/withcatai/node-llama-cpp/issues/595) (anecdotal, single report)

### Inferences
- Because a heap sub-allocation in a set makes the whole heap resident, heap-backed expert pools wire all-or-nothing; per-expert residency needs one buffer (or one placement-sparse mapping) per expert group.
- Metal 4 placement sparse buffers backed by placement heaps are the documented mechanism closest to "map only the hot experts"; no engine was found using them for LLM weights.
- A cheap keep-alive GPU command (or MLX's refresh interval) is the published technique against residency being dropped after idle; it also sidesteps the teardown leak.

### Gaps
- No primary source describes how the driver wires a no-copy buffer over a file-backed mmap (whole buffer at first use vs per page), purgeable-state behaviour for shared buffers on Apple silicon, or the jetsam / memory-pressure policy for wired GPU memory on macOS 26/27.
- The exact default of `recommendedMaxWorkingSetSize` as a fraction of RAM per machine size was not confirmed from Apple documentation.
- Whether Metal 4 command buffers retain resources was not stated in the fetched session text.

## 6. GPU power and performance management visible to developers

### Takeaway
Developers can observe GPU DVFS only indirectly, through `powermetrics` (requested vs applied software state, frequency residency) and unprivileged IOReport readers of the "GPU Stats / GPU Performance States" and "Energy Model" groups; no published, verified technique for holding the GPU clock up during bursty LLM decode was found.

### Cited Findings
- `powermetrics --samplers gpu_power` reports average GPU frequency per sample, percentage active residency at each frequency and two software states (requested and applied). On M4 Pro (20 GPU cores) maximum frequency was 1,578 MHz with requested state P10; on M3 Pro (18 cores) 1,380 MHz with requested P8. — [Eclectic Light, 6 Jan 2025](https://eclecticlight.co/2025/01/06/power-modes-and-apple-silicon-gpus/)
- Low Power Mode on M4 Pro caps GPU frequency at 1,056 MHz (67%), applied state P4 to P5, GPU power about 20 W to about 6 W, Blender performance 65 to 71% of normal (about 32% of the power for about 69% of the performance); High Power Mode changed nothing measurable except fans; on M3 Pro Low Power Mode did not change GPU control. Peak GPU power in a 0.1 s sample was 25.3 W. — [Eclectic Light, 6 Jan 2025](https://eclecticlight.co/2025/01/06/power-modes-and-apple-silicon-gpus/)
- Unprivileged tools read IOReport: agtop subscribes to "Energy Model" (nanojoules per interval), "CPU Core Performance States" and "GPU Performance States" (GPUPH residency, frequency as a residency-weighted average); macmon and SocPowerBuddy read CPU/GPU power, frequency and residency without sudo. — [agtop (index page)](https://awesome.ecosyste.ms/projects/github.com%2Fbinlecode%2Fagtop), [macmon sources.rs](https://docs.rs/crate/macmon/latest/source/src/sources.rs), [SocPowerBuddy](https://github.com/BitesPotatoBacks/SocPowerBuddy)
- A developer reports that `powermetrics` GPU power is far below total system DC power on M4 Max under GPU compute and asks whether some activity is not attributed to the GPU rail; unresolved. — [Apple Developer Forums 819927](https://developer.apple.com/forums/thread/819927)
- Apple's tooling for kernel authors: Metal System Trace "Performance Limiters" counters including Neural Accelerator utilization. — [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- llama.cpp's author noted that sustained M5 runs "may heat-throttle" when quoting about 2.5x prefill gains. — [llama.cpp PR #16634](https://github.com/ggml-org/llama.cpp/pull/16634)
- Energy efficiency of GEMM on M-series was benchmarked with `powermetrics` in an HPC-oriented study. — [arXiv 2502.05317](https://arxiv.org/html/2502.05317v1)

### Inferences
- Low Power Mode is the only documented user-level control that changes GPU frequency, and its roughly 3x power cut for about 30% less throughput (M4 Pro, Blender) suggests a large energy-per-token saving is available for compute-bound phases; for bandwidth-bound decode the trade may be even better, but this is untested in the sources.
- Since the requested state stayed at the maximum under steady load, clock-down in bursty decode is most plausibly a utilization-driven governor effect; keeping the GPU continuously fed (fewer, larger command buffers; no idle gaps between tokens) is the only lever implied by the sources.

### Gaps
- No source was found on GPU idle-to-ramp latency, on how bursty per-token workloads are clocked down, or on any API to pin a GPU performance state.
- No documentation was found for IOReport PMP / DCS memory-bandwidth counters; they remain unconfirmed.
- No published energy-per-token study of MLX or Metal LLM decode with per-rail attribution was found.

## 7. Alternatives and complements to MLX on the Mac in 2026

### Takeaway
Apple now positions three stacks: Core AI (new at WWDC 2026, the successor to Core ML for neural networks, with custom Metal kernels and CPU/GPU/Neural Engine execution), MLX (research, training, open source) and Metal TensorOps underneath both; llama.cpp adopted the Metal 4 tensor path for M5 in November 2025, and a standalone Metal runtime (BaseRT) currently reports the best published MoE prefill numbers on M5.

### Cited Findings
- Core AI: announced at WWDC 2026 as "the next evolution of on-device AI execution", the framework behind Apple Intelligence and the new Siri; pure inference; models are `AIProgram` assets converted from `torch.export` programs via `TorchConverter().add_exported_program(ep).to_coreai()`; specialized for the device at first load and cached, or pre-compiled ahead of time; Swift API with `NDArray` inputs/outputs, pre-allocated states and outputs, async pipelines, zero-copy paths; supports custom Metal kernels (registered from Python as `TorchMetalKernel`); quantization and palettization through Core AI Optimization; runs across CPU, GPU and Neural Engine; a Core AI language model can be used through the Foundation Models `LanguageModel` protocol. Core ML remains for classic ML such as decision trees. Ships with the OS 27 generation; the article gives no exact version. — [WWDC26 session 382](https://developer.apple.com/videos/play/wwdc2026/382/), [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/), [InfoQ, 20 Jun 2026](https://www.infoq.com/news/2026/06/apple-core-ai-wwdc/)
- A third-party benchmark reported Core AI 2.47x faster than MLX on tiny models but only 1.05x at 8B (Qwen3 8B, M4 Max) with near-parity decode. — [Wccftech](https://wccftech.com/apples-new-coreai-engine-barely-edges-out-its-own-mlx-framework-at-realistic-8b-model-sizes-despite-being-2-47x-faster-on-tiny-models/) (secondary; page could not be fetched, figures from search summary; unconfirmed)
- Apple's stack description (WWDC 2026): Core AI and MLX on top, then Metal Performance Shaders, then MPP / TensorOps; MPS, MPSGraph and Core ML pick up Neural Accelerators automatically; MLX, llama.cpp and PyTorch are named as open-source tools already using them. — [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/), [Apple tech talk 111432](https://developer.apple.com/videos/play/tech-talks/111432/)
- llama.cpp: PR #16634 "metal : initial Metal4 tensor API support" (opened 17 Oct 2025, merged 6 Nov 2025) reworks mat-mat multiplication (including the `mul_mm_id` MoE path) on the tensor API, with run-time detection, an env var to disable it, and use "only on M5 and later"; reported gains about 2x prompt processing (gpt-oss 20B pp512 about 847 vs 415 t/s; Llama 8B Q4_0 pp2048 about 540 vs 248 t/s), author estimate about 2.5x. — [llama.cpp PR #16634](https://github.com/ggml-org/llama.cpp/pull/16634)
- LM Studio's bundled llama.cpp runtime 2.21.0 did not enable the Metal 4 tensor API on M5 / macOS 26.2+, while upstream b9592 did and was 2 to 3x faster in prompt processing per the reporter. — [LM Studio bug tracker #2040](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040)
- BaseRT (native Metal runtime, v0.1.6, Jul 2026): up to 6.4x llama.cpp and 3.9x MLX in prompt processing on M5 Pro, largest margins on MoE; decode up to 1.75x llama.cpp and 1.33x MLX; code public. — [arXiv 2607.19438](https://arxiv.org/abs/2607.19438)
- Comparative study (M2 Ultra 192 GB, Qwen-2.5, submitted 9 Oct 2025): MLX highest sustained generation throughput; MLC-LLM lower TTFT for moderate prompts and stronger built-in inference features; llama.cpp efficient for lightweight single-stream use; Ollama trails; PyTorch MPS memory-limited. — [arXiv 2511.05502](https://arxiv.org/abs/2511.05502)
- ExecuTorch: an MLX delegate (experimental, blog updated 15 May 2026) dispatches about 90 ATen ops to MLX's Metal kernels and claims 3 to 6x the throughput of existing ExecuTorch delegates on macOS; before it, macOS users had XNNPACK (CPU) or the AOTI Metal backend. — [PyTorch blog](https://pytorch.org/blog/running-pytorch-models-on-apple-silicon-gpus-with-the-executorch-mlx-delegate/)
- Porting limits: "Public Metal lacks asynchronous copy, and batch-one decode makes several serving-oriented mechanisms inapplicable"; transferable ported CUDA kernel ideas gave up to 1.20x decode on Apple hardware. — [arXiv 2610.31479](https://arxiv.org/abs/2610.31479)

### Inferences
- For a Mac-only MoE engine the practical choices are (a) MLX with custom `metal_kernel`s (fast to iterate, but bound by MLX's command-buffer policy, allocator and JIT kernel signature), (b) raw Metal 4 with TensorOps (BaseRT's route; best published M5 prefill), or (c) Core AI with custom Metal kernels (Apple-supported deployment, Neural Engine access, but closed scheduling and OS 27 only).
- On pre-M5 hardware none of the alternatives has a hardware advantage over MLX; differences come from kernel fusion, tile choice and scheduling overhead.
- Core AI's near-parity with MLX at 8B suggests both sit on the same Metal kernels for large models, so Core AI is not obviously a faster base for a custom engine.

### Gaps
- No 2026 primary source was found on MLC-LLM / WebGPU progress on Apple silicon, on MPSGraph changes in OS 27, or on ExecuTorch's older MPS delegate status.
- Core AI's minimum OS version, its handling of MoE models and whether it exposes Neural Engine execution for LLMs larger than a few billion parameters were not confirmed.
- The llama.cpp env var name for disabling the tensor API (`GGML_METAL_TENSOR_DISABLE` per a string seen in a binary) is unconfirmed, as are later 2026 llama.cpp Metal changes.
